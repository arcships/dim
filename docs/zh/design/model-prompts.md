# 面向模型的提示词

状态：草案（[#429](https://github.com/arcships/dim/issues/429)）。本文是需求，不是设计：它定下产品写给模型的文字要达到什么、每条文字走哪条通道、哪些是协议、哪些是策略、谁能改哪一层，以及一次改动怎样判定；各部分由各所有者自行设计（§9）。范围：模型从产品读到的全部文字——system 前缀、规则与状态块、工具声明、运行时写入的标记、压缩替换和输入指南——覆盖一个 Session、它的分支和它的插件。English: [English](../../design/model-prompts.md)。

模型读到的文字与运行时一致、能分清操作者的话和运行时加的内容、产品又能凭依据调整行为时，模型才会按产品期望的方式工作。本文回答 [#429](https://github.com/arcships/dim/issues/429) 的五个问题（由 [Agent 上下文 §3](../../design/agent-context.md#3-给模型的提示词) 提出），并把结论交给每条文字的所有者。

## 1. 回答

**策略与协议。** 按模型读它的方式读这段文字，然后只改字：改后句子对运行时变成假话，或某个机制照原样就用不了，这段文字是**协议**；否则是**策略**。协议是机制面向模型的那一面——通道名与标记名及其属性值、`[input <id>]` 这类句柄、拒绝码、工具 schema 与结果格式，以及陈述运行时保证的句子。协议文本会被记进事实——历史与被采用的配置——所以改动它之后，用旧形式恢复的历史仍要能读懂，否则对该文字的所有者来说就是一次记录格式变更；同时它与所描述的行为、断言该行为的流程测试同一个改动落地。策略是怎样做事的指导：可替换，每次改动都要评估（§8）。一段文字可以两者都有，例如带 schema 和描述的声明；分类按句子判定（§4）。

**谁能改什么。** 每个作用域只通过自己拥有的通道到达模型：产品通过它的内建能力；宿主或 profile 通过 Session 的 system prompt 和它加载的可信来源；项目通过它的 `AGENTS.md` 和 skills；用户通过自己的消息、`~/AGENTS.md` 以及选择取值的设置；插件通过与内建能力相同的通道注册或写入的内容。没有哪个中心仓库能把措辞从作者手里拿走：Prompt、PromptRegistry 和 ToolRegistry 只承载、从不拥有（原则 §1、§5；ADR 002）。任何作用域都不改协议、不改别人的文字，标签从不授予权限，指南的框架谁都删不掉，System 只放静态文字（§5）。

**输入指南。** 输入指南是向模型解释其余通道的那段文字：每条通道的信任类别、通道规则、转义、摘要之后的重述，以及每个标记——它是什么、是谁的话、怎么对待、什么时候失效、属于哪条信任规则（§6）。它的框架归 prompt 层，也就是 Prompt。每个标记的条目由写该标记的能力贡献，走每一份贡献都走的路——在自己的 `apply` 里注册、卸载时撤回——所以条目在它的写入者装载时恰好生效，贡献上来的插件也一样；一份固定的文字永远覆盖不了它们。生效的条目必须能从事实重建；条目在它的写入者装载处出现，所以没有条目会让会话中途的缓存前缀分叉；这两点 Prompt 怎么做到，是 Prompt 的设计。没有采用配置的宿主准备请求带着同一份组合，那里指南只在写入者装载或卸载时变化（§6.2）。一致性由构造保证：没装载的写入者不贡献条目；已装载写入者自己的流程断言承载其标记的请求也承载它的条目；删改标记时同一个改动里改它的条目。没有中心扫描，也没有中心标记清单。

**语言。** 面向模型的文字——协议与策略一样——一律英文、单份：每份策略文本对应一次评估，多一种语言每份文本和它的评估都翻倍，按语言变化的文字会让 Session 的缓存前缀和它的证据一起分叉，而且任何译文里协议名还是英文。"Agent prompt language"是模型写给操作者的文字所用的语言，以运行时状态来源投递；它既不是对提示词文本的翻译，也不是在多份译文之间选择；没有设置时，base 里那句"模型用用户的语言回答"就是默认。摘要与标记正文是数据：保持会话的语言，标识符逐字保留（§7）。

**判定一次改动。** 策略文本的改动对照当前文本判定：同样的用例、同样的模型与推理、同样的预算、两臂同一个固定判分模型；每个比较项都按当前臂检验是否回退——落败超过 `δ = 0.05`，且两臂计数上的单侧 mid-p Fisher 精确检验拒绝「没有落败」；一个在任何数据之前固定的族用 Holm 在族错误率 `α = 0.10` 下校正；判定是三值的 `fail`、`pass` 或 `inconclusive`，每臂每个用例至少 20 次已判运行才可能是 `pass`；候选文本自己的 token 成本与分数并列报告，不用绝对通过线（§8.1）。候选走 shipped 装配：放在它作者的工厂配置里，绝不在评估专用路径里改字符串。摘要提示词有 `summary-eval --candidate`；行为类文本用场景评估，形式同 [Timeline 分支 §12.3](timeline-branches.md#123-评估场景)；还没有评估装置的文本，改动自带场景集，本地跑完写在 PR 里。没有文本因为没有装置而被冻住（§8）。

## 2. 依据

1. **模型读到的是事实的投影。** 模型上下文里只有交接之后被消费的事件——已采用的输入、工具结果、已采用的提示词——分支采用的那份配置另外带来 system 前缀和工具声明（原则 §4 第 6 条）。所以每条文字都经由下面一小撮固定通道之一到达模型（§3），上下文里没有别的东西。

2. **通道有承载者，每条文字有作者。** 承载者只投递，从不拥有措辞；作者注册或写入文字，并拥有它。文字归在它的状态所在之处，是插件契约自己的规则（原则 §5、ADR 002 D1）：中心文本仓库会把措辞从它所描述行为的模块手里拿走。

3. **不同通道的信任不同。** 规则在其作用域内约束，状态描述情况，标记是信息、从不是权限，操作者的话属于操作者，工具材料是材料。模型必须能分清自己读的是哪一种，指南就是告诉它的地方（§6）。

4. **策略与协议按不同的依据改动。** 策略凭评估改（§8）；协议随它所描述的行为改，而记下它的那些事实要让旧形式仍然可读（§4）。

5. **通道是封闭的，作者是开放的。** 新开一条通道会改变运行时的投递方式，属于原则 §4 第 8 条的基础设施变更；文字靠成为现有通道的作者加入，内建能力与贡献插件都一样。而因为作者是开放的，指南的条目由写入者贡献、不是一次写死，一份固定的文字因此不必覆盖贡献插件的标记（§6）。

## 3. 通道

每条模型可见的文字都落在下表的某一条通道里。表里给出承载者、作者、生命周期与信任类别；§4 与 §5 都建立在它之上。

| 通道 | 承载者 | 作者 | 生命周期 | 信任 |
| --- | --- | --- | --- | --- |
| system 前缀 | Prompt：注册的 System 来源，在根分支启动时采用 | base：PromptSources；Session 的 system prompt：宿主或 profile；skills 指令：Skills | Session 内静态 | 指令 |
| 规则与状态块（`<dim-rule>`、`<dim-state>`） | Prompt：Append 输入、带 key、压缩后重放 | 该来源所属的能力；用户与项目指令的正文是用户或项目自己的 | 按 key：被替换、撤回或过期 | 规则：在作用域内约束。状态：情况 |
| 工具声明 | ToolBinding 与 ToolRegistry：配置的 tools 部分 | 每个工具的所有者，内建或贡献 | 已采用的配置 | 该工具的指令 |
| 运行时写入的输入（标记） | 输入路径：InputQueue，然后 Loop | 写它的能力——TimelineTree、Collaboration、BackgroundExec、ShellInput，以及每个贡献插件 | 历史条目；压缩可能替换它们 | 信息，从不是权限 |
| 操作者输入 | 输入路径 | 操作者 | 历史 | 操作者的话 |
| 工具结果 | Loop | 来自外部的材料；运行时写进结果里的拒绝与句柄归该工具的所有者 | 历史 | 材料，从不约束；skill 工具的结果是唯一例外 |
| 压缩替换 | ContextPolicy | 摘要：策略；清单与钉住输入及其句柄：ContextCompaction | 替换一段历史 | 背景；现场对话优先 |
| 输入指南 | Prompt：它组合、由 Session 采用的 System 的一部分；宿主准备的请求带同一份组合 | 框架：Prompt；每个标记的条目：写该标记的能力（§6） | 在其写入者的两次装载之间固定；条目在写入者装载处生效、在卸载处结束 | 关于其余通道的指令 |

**核对。** 现有文字都落在表内，不需要新通道：base、Session 的 system prompt 与 skills 指令在 system 前缀；环境与日期状态、用户与项目指令、skills 列表是规则与状态块；每个内建工具声明，以及 MCP server 与贡献插件的声明，在配置的 tools 部分；分支、goal、exec、协作、shell 输入、Scheduler 与 Workflow 的标记是运行时写入的输入；操作者的消息；工具结果，连同运行时写进其中的拒绝、错误码与句柄；摘要、清单与钉住输入在压缩替换里；以及指南本身。哪条文字都落不进去，才需要新通道，那是基础设施变更（原则 §4 第 8 条）；没有这样的文字。

## 4. 协议与策略

**判据。** 按模型读它的方式读这段文字，然后只改字。

- 改后的句子对运行时变成假话，或某个机制因此用不了——模型放不对标记、调用形状不对、看不懂某个错误码——这段文字是**协议**。
- 运行时行为一模一样，只是模型选择怎么做的方式变了，这段文字是**策略**。
- 文字是操作者、项目或某个 profile 自己的话，它是**内容**：产品转义后承载，从不编辑。

**协议**是机制面向模型的那一面：

- 通道名与标记名、属性及其取值（`op`、`cleared` 等）；
- `[input <id>]` 这类句柄；
- 拒绝码；
- 工具 schema 与结果格式；
- 陈述运行时保证的句子。

由此有三条要求。协议只随所描述的行为一起改，并且与断言该行为的流程测试同一个改动。因为它记在事实里——历史与被采用的配置——改动要让用旧形式恢复的历史仍然可读；做不到时，对该文字的所有者就是一次记录格式变更。改它的所有者要写明自己保持了哪种兼容。

**策略**是怎样做事的指导：base 的规则、shell 指导、工具声明里的用法指导、分支与协作工具的协调文字、Goal 的措辞、摘要提示词的措辞。它可替换，每次改动都要评估（§8）。

**混合文本。** 一段文字可以两者都有。工具声明是最常见的情形：schema 与结果格式是协议，描述里的指导是策略。分类按句子，所有者在自己设计页上标出拆分（§9.2）。

## 5. 作用域

| 作用域 | 通过什么到达模型 | 限制 |
| --- | --- | --- |
| 产品 | 它内建能力的文字 | 不随行为不改协议，不改别人的文字 |
| 宿主或 profile | Session 的 system prompt，以及经由宿主的提示词加载装入的可信来源 | base 与 skills 指令不是它能删的；指南追加在它之后 |
| 项目 | 项目的 `AGENTS.md`，按 project scope 规则承载，以及项目的 skills | 不改协议，项目规则不授予权限 |
| 用户 | 自己的消息；`~/AGENTS.md` 按 user scope 规则承载；选择取值的设置——模型、执行 shell、回答语言、摘要的推理设置（[ContextCompaction §13.2](plugins/ContextCompaction.md#132-summaryreasoning)） | 不改协议，用户规则不授予权限 |
| 插件，内建或贡献 | 它注册或写入的文字：来源、工具声明、标记，以及它们的指南条目 | 同样的限制，并且不能贡献不属于自己标记的条目 |

对每个作用域都成立的三条限制：

1. **任何作用域都不改协议、不改别人的文字。** 协议随它的行为改（§4），文字归它的作者（§2 第 2 条）。
2. **指南的框架不可移除。** 框架——通道、信任、转义、通道规则、重述——归 Prompt，任何操作者、项目、插件或 profile 都删不掉、换不掉（§6）。
3. **System 只放静态文字。** 会话期间会变的文字以规则或状态输入到达，缓存前缀在 Session 内保持一份（§7）。

用户或项目的话在它的作用域内影响模型怎么做；它们从不改变运行时行为，也从不授予权限。标记里的内容是材料，标签描述内容，不授权（§6）。

## 6. 输入指南

输入指南是模型每次请求都会读到的、关于自己输入的那段文字。

今天它是一份固定文字——框架加上内建标记的条目——由请求组装追加到 system 字段：ContextPreparation 在发布随采用配置一起的 System 时追加，Loop 在没有采用配置的宿主准备路径上追加（[提示词生命周期](../../architecture/rust-agent/prompt.md)）。凡由采用配置构建的请求都带着它，摘要请求也包括在内。

### 6.1 覆盖什么

- **每条通道的信任类别**：指令、在作用域内约束的规则、描述情况的状态、信息、材料，以及操作者的话。
- **通道规则**：操作者的话只出现在他们自己的消息里，运行时添加的一切都单独到达、带标记、经过转义。唯一例外是压缩追加到被缩短输入上的 `[input <id>]` 句柄，recall 工具按它打开全文。指南里"运行时添加的一切都在单独的消息里到达"那句话（[input-guide.txt:5](../../../crates/dim-agent-capabilities/src/input-guide.txt)）与这个句柄矛盾；要求的规则是更正后的那条。
- **转义**：运行时之外的内容伪造不出标记；标记内部未转义的标签是运行时自己放的。
- **摘要之后的重述**：摘要之后的 state 与 rule 是仍然生效的版本，不是新的变化。
- **对每个标记**：它是什么、是谁的话、怎么对待、什么时候失效、属于哪条信任规则。

### 6.2 各部分归谁

- **框架**——通道、信任类别、转义、通道规则与重述——归 prompt 层，也就是 Prompt。
- **每个标记的条目**由写该标记的能力贡献。它走每一份贡献都走的路：在贡献者自己的 `apply` 里注册，贡献者卸载时撤回，所以条目在它的写入者装载时恰好生效（[PromptRegistry](../../architecture/rust-agent/plugins/PromptSources.md#promptregistry)；[rutis 用法 R6](rutis-usage.md#r6-贡献向所有者登记)）。这条路由是一份语言中立的契约（§9.1），所以经插件桥接贡献的插件用同样的方式贡献条目；一份固定的文字永远覆盖不了它们。
- **Prompt 提供手段。** 它接收条目、与框架组合成它发布的 System；生效的条目能从事实重建，和其余来源一样。指南是那份 System 的一部分：条目在其写入者装载时生效、在卸载时结束，因为 Prompt 在每个组合发生变化的开放分支上采用指南，而那些时点之间指南固定，所以没有条目会让会话中途的缓存前缀分叉。写入者的工具声明可以比它的条目早一步到达请求：工具的来源一装载就经工具采用绑定，条目则经指南采用到达，所以落在这段窗口里的一步带着新工具和上一个 System，下一步再把 System 移动一次。设计接受这一步的窗口，而不是让 Loop 等待待处理的采用。具体机制是 Prompt 的设计（§9.1）。
- **指南随 System 一起到达。** Loop 与 ContextPreparation 什么都不自己追加：由采用配置构建的请求带着 Prompt 组合好的 System，ContextPolicy 则从采用配置里读同一份 System 来构建摘要请求。
- **宿主准备的路径带同一份组合。** 宿主在没有采用配置的情况下准备的请求，带着 Prompt 为已装载的写入者组合好的指南——框架与它们的条目——也就是采用的 System 所带的那同一份组合，所以今天由这条路径送达的内容一样不少。在这条路径上，指南只在某个写入者装载或卸载的地方变化，而那正是这条路径的工具声明改变请求的时点（它经 ToolBinding 逐请求绑定工具），也正是采用路径采用指南的时点，所以两条路径上都没有条目会让缓存前缀分叉。两条路径怎样读到同一份组合，是 Prompt 的设计（§9.1）。

### 6.3 一致性由构造保证

- 没装载的写入者不贡献条目，所以条目不会比它的写入者活得久。
- 条目在它的写入者装载处出现：由采用配置构建的请求在装载所触发的那次指南采用处，宿主准备的路径则在装载本身；没有请求自己组装指南。
- 分支在自己的 open 处采用一次指南，因为 fork 继承父分支的配置、恢复的分支承载它持久化的 System：这次采用是 open 的一部分，所以分支从第一条请求起就按写入者装载时登记的条目运行，代价是每次 open 读一次上下文。
- 关闭中的分支什么都不采用：写入者正因为它要关停而卸载，所以分支从未运行过的 System 不会被记录。
- 已装载写入者自己的流程断言：承载其标记的请求也承载它的条目。
- 删改标记时，同一个改动里改它的条目。
- 没有中心扫描，也没有中心标记清单。

## 7. 语言

**面向模型的文字一律英文、单份，协议与策略一样。**

- 每份策略文本对应一次评估（§8）；多一种语言，每份文本和它的评估都翻倍，两份语言还会各自漂移。
- system 前缀是 Session 的缓存前缀；按语言变化的文字会把前缀和它的证据一起分叉。
- 协议名、属性值和错误码由运行时各只有一种拼法，译文里照样是这些英文名字。
- 指令遵循在不同语言间不等价，产品不为它没跑过的评估背书。

**"Agent prompt language"** 是模型写给操作者的文字所用的语言。它解决的是操作者环境语言与消息语言不一致的情形——中文会话里粘进英文日志或代码，或者第一条消息是资料而不是请求——回答语言从此是显式选择，而不是从最后一条消息推断。要求是：

- 取值以一个状态来源到达模型，写明模型写给操作者所用的语言；块的形态是 PromptSources 的设计（§9.1）。
- 没有设置时，base 那句规则成立：模型用用户的语言回答。
- 它是操作者的设置；项目要指定语言，就写在自己的规则里，那是内容。

否决：按 locale 翻译提示词文本。它让策略文本和它们的评估翻倍、让缓存前缀分叉，而协议名照样是英文。

**数据保持自己的语言。** 摘要、目标、分支的目的和工具结果保持它们来时的语言；每个标识符——路径、符号、命令、错误——在任何语言下都逐字保留（[压缩需求 §3](compaction-quality.md#3-压缩保住什么)）。

## 8. 一次改动怎样判定

### 8.1 规则

**对照。** 策略文本的改动对照当前文本判定：同样的用例、同样的模型与推理设置、同样的预算——同样的窗口、工具、轮数上限和起始工作区——两臂用**同一个固定判分模型**。一个比较项是候选臂相对当前臂在一个比率上的落败：落败不超过 `δ = 0.05` 就从不判为回退；更大的落败在两臂计数上的单侧 mid-p Fisher 精确检验拒绝「没有落败」时才算回退。每次评估有一个在任何数据之前固定的比较族：

- 每个（场景、探针）——`must_show` 探针用通过率，`must_not_show` 探针用违规率；
- 汇总的 `must_show` 通过率与汇总的 `must_not_show` 违规率，用来发现摊薄在许多探针上的落败；
- 失败运行率与未判运行率。

探针的比率只计已判且未失败的那些运行；失败运行只比较一次，即失败运行率。Holm 在族错误率 `α = 0.10` 下校正该族：按 p 值升序排第 `i` 位的比较项，其阈值为 `α / (m − i + 1)`；一旦有一项未能拒绝，其后的都不再拒绝。候选文本自己的 token 成本（每次请求都带上）与分数并列报告。不使用绝对通过线：绝对线——任务成功率，或非确定性模型上的一个判分——随场景、模型和运行波动，需要很多次运行才能把差异和噪声分开，而同预算下的相对比较在各场景上都成立（[压缩需求 §6](compaction-quality.md#6-怎样判断压缩做得好)）。判分模型随结果写明；与模型同家族的判分模型作为测量的局限报告。

**判定。** 任一比较项是回退就是 `fail`，与运行次数无关；否则，下限未满足或某个比较项无法做出时是 `inconclusive`；其余是 `pass`。下限数的是**已判运行**：每臂对每个场景或用例至少要有 20 次。失败运行与未判运行不进任何探针比率，它们在自己的行里比较，但不计入下限——下限是为探针比率比较的效力而设，只有已判运行才进入这些比率。某个比较项在某一臂一次计数都没有时，它无法做出：用例集里有的某种探针，如果在一臂里全部是失败或未判运行，判定就是 `inconclusive`，因此没有 `pass` 会建立在从未判分的数据上。整个用例集都没有的探针种类不是这种情况，它不进这个族，因为两边都没有可比的东西。

**实测的极限。** 该规则在 210 条已记录的运行上实测，按整次运行重采样——每次运行的探针一起——每场景每臂 20 次运行、每个用例 10,000 次试验；方法与测量结果见 [#729](https://github.com/arcships/dim/issues/729) 的“Why this rule”：

| 用例 | 被判为回退的比例 |
| --- | --- |
| 完全相同的文本 | 0.7% |
| 一个 `must_show` 探针从 1.0 掉到 0.5 | 98% |
| 每个探针都落败 0.15 | 87% |
| 一个 `must_not_show` 探针的违规率从 0.1 升到 0.4 | 36% |

最后一行就是规则在下限处的极限：要以 80% 的概率发现它，每场景每臂需要约 44–51 次运行。因此报告为每个比较项打印两臂的计数、两个比率、落败、p 值与 Holm 阈值，读者既能看见规则标出的落败，也能看见它没有标出的落败。实测表按整次运行重采样，每次运行的探针因此保持在一起。汇总行不是：它把每次运行的每个探针算作一个观测，而同一次运行的探针共享一份对话记录，所以这些 p 值偏乐观。偏乐观的方向是多判回退，也就是多判候选失败；逐探针的行则是同一个探针跨整次运行比较。

**失败运行与未判运行。** 失败运行是结束于错误或墙钟预算的那次运行，或者判分没有发生的那次：没有能交给判分模型的东西，或者判分调用失败——窗口溢出、传输错误或 HTTP 错误，或回复在输出上限处被截断。未判运行是判分模型回答了、但两次重问后仍给不出可用结论的那次运行，或者视图放不进判分模型预算、因此从未被询问的那次运行：它不计入所在臂的任何探针比率，报告会统计、连同原因一起列出它；未判运行率比较它。失败运行同样不在探针比率里，只比较一次，即失败运行率。重问得到的结论来自同一个判分模型、同样设置下更长的一段对话，两臂按同一规则重问。一次运行的判分读的是它导出的一幅视图：每条请求对照同一行上前一次请求给出——自那次请求以来新增的消息，历史变化后则是整份消息列表——请求的其余字段只在变化时完整给出，未变化时读作未变化标记，因此不丢弃任何东西。判分模型一次调用读完这幅视图。视图放不进判分模型声明的窗口（扣除回复的 `maxTokens`）时不分部分判分：统计、排序或贯穿整次运行的探针无法从单独一部分回答，因此该运行在做出任何调用之前就是未判运行，报告给出估算与预算。估算由 runner 自己在调用前给出，因此预测的溢出从不被询问。因窗口溢出被提供方拒绝的调用则说明声明的窗口或估算有误，它仍是失败运行：拒绝是运行超出模型真实窗口的显现方式，而失败运行数在两臂之间比较。场景判分模型被要求回答 `present` 或 `absent`；场景评估与摘要评估共用的判定解析器也接受 `contradicted`，`must_not_show` 探针把它视为没有出现。判分模型没有声明窗口的评估在第一次调用之前就失败。

**候选走 shipped 装配。** 它放在作者的工厂配置里，就像摘要策略可选的 system prompt 成员（[ContextCompaction §13.4](plugins/ContextCompaction.md#134-评估)）让候选提示词替换固定那份——产品配置从不设置它——绝不在评估专用路径里改字符串；两臂因此跑的都是 shipped 的请求构建、分块与失败处理。

**在哪里跑。** 真模型运行在本地，结果写进 PR。CI 只保留确定性的协议检查。

### 8.2 评估装置

- **摘要提示词与它的长度指令**有 `summary-eval --candidate`：同样的用例、模型和目标规则下对照当前与候选（[ContextCompaction §13.4](plugins/ContextCompaction.md#134-评估)）。
- **行为类文本**用场景评估，形式同 [Timeline 分支 §12.3](timeline-branches.md#123-评估场景)：脚本化输入、真实工具、对"必须出现"和"不得出现"的探针，两臂交给固定判分模型。对评估工具的要求是一个场景运行器，带同样的候选注入和同样的检验（§9.8）。
- **还没有装置的文本，改动自带场景集**，本地当前对照候选跑完，写在 PR 里。没有文本因为没有装置而被冻住。
- **协议文本不评估。** 它的流程测试随它一起改（§4）。

## 9. 向各所有者提出的需求

格式沿用 [Timeline 分支 §17](timeline-branches.md#17-向机制所有者提出的需求)。所有者改自己的文档。

### 9.1 Prompt、PromptRegistry 与 PromptSources

**所有者：** Prompt、PromptRegistry 与 PromptSources；在 [#548](https://github.com/arcships/dim/issues/548) 下实现。

- Prompt 拥有指南的框架（§6.2）并审定它；任何作用域都删不掉、换不掉。
- 框架写明通道规则及其 `[input <id>]` 例外（§6.1）。
- Prompt 提供能力贡献其标记条目的手段：在贡献者自己的 `apply` 里注册、卸载时撤回；生效条目能从事实重建；条目在写入者装载或卸载处生效或结束，其间指南固定，并在每个分支的 open 处采用一次、在每个组合发生变化的开放分支上采用，组合没有变化的分支保持原样（§6.2）。机制由 Prompt 设计。
- **贡献通道是一份契约。** 它的形态语言中立，所以经插件桥接贡献的插件同样能贡献其标记条目，而 Rust 只是它的一个绑定（ADR 002 D5、ADR 006）。本文只把这份契约提给 Prompt，不定义它；它的形态是 Prompt 的设计（§10）。
- **组合只有一份。** 框架与生效的条目是一份组合，采用的 System 与宿主准备的请求都带着它；宿主准备的路径怎样读到它，是 Prompt 的设计，在 ADR 002 D3 之内。
- PromptSources 把 `dim/base` 与 shell 指导保持为策略，放在它的工厂配置里以便候选运行（§8.1）；环境与日期来源只陈述事实；指令正文是用户或项目的话，转义后承载、从不编辑。
- PromptSources 提供"Agent prompt language"的状态来源，块的形态由它设计（§7）。
- Prompt 与 PromptRegistry 只承载文字，不拥有任何一条（§2 第 2 条）。

### 9.2 每个写入面向模型文字的能力

**所有者：** 每个写入文字的能力——内建的或贡献的；在 [#551](https://github.com/arcships/dim/issues/551) 下实现。

- 它在自己设计页上列出它的面向模型文字，逐条标明协议或策略，混合的按句子标明。本文不重复这些清单，正如 [Timeline 分支 §12.1](timeline-branches.md#121-上下文映射) 对它自己的文字所做的那样。
- 它为它写的每个标记贡献指南条目，并且它自己的流程断言：承载该标记的请求也承载该条目（§6.3）。
- 它把策略文本放在自己的工厂配置里，好让候选走 shipped 装配（§8.1）。install 调用注册该配置的名字并提供其值；profile 不调用它而放置的 part 既不声明也不读取，内置文本生效。
- 协议改随行为、流程测试、以及旧形式恢复历史的兼容一起交付（§4）。

SessionTitle 不在范围内：它的 `SYSTEM`（`runtime/plugins/session-title/index.ts`）是辅助标题调用的 system 文本，不进入 Session 的模型上下文——标题请求不是 Session 请求（§3 的通道）。

### 9.3 ToolRegistry 与 ToolBinding

**所有者：** ToolRegistry 与 ToolBinding；在 [#549](https://github.com/arcships/dim/issues/549) 下实现。

- 它们承载声明，不拥有任何措辞。

- 声明的策略改动按 §8，协议改动按 §4。

### 9.4 TimelineTree

**所有者：** TimelineTree；在 [#552](https://github.com/arcships/dim/issues/552) 下实现。

- **协议。** 标记名与属性、身份块里的事实句、branch 工具的 action 与 mode、以及它的拒绝码，只随分支机制一起改，并与断言它们的流程测试同一个改动（§4）。
- **`main` 的协调文字覆盖 [Timeline 分支 §12.2](timeline-branches.md#122-交给提示词层的事项429) 的事项。**
- **评估。** 这些文字是策略：改动用 [Timeline 分支 §12.3](timeline-branches.md#123-评估场景) 的场景评估——重做工作、过度拆线、刷屏、不肯结束、兄弟转达、乒乓、压缩后的身份、直接问用户——当前对照候选（§8）。

### 9.5 Goal

**所有者：** Goal；在 [#553](https://github.com/arcships/dim/issues/553) 下实现。

- **措辞。** 一条线不是被委派的工作：它是同一个 agent 在本 Session 的另一条线上（[Timeline 分支 §1](timeline-branches.md#1-分支用来做什么)）。要求：目标块与续跑块的句子（[Goal §A.5](plugins/Goal.md#a5-模型可见文本)），以及 [Goal §3.4](plugins/Goal.md#34-新分支清除继承的目标) 和 [Goal §5](plugins/Goal.md#5-上下文映射) 子分支那一行里的陈述，都写 "on another line of this Session"，含义不变——目标属于另一条线，这条线既不续跑它，也不为它调用 `goal_update`。任一句的改动都是一次策略改动，按 §8 判定（[Goal §A.5.2](plugins/Goal.md#a52-评估)）。
- **分类。** 标记名、`kind` 取值与 key 是协议；上面那些句子是策略。
- **指南。** Goal 在写它的标记时贡献对应的条目（§6.2、§9.2）。
- **评估。** 一套目标场景——在 `main` 上设的目标会续跑；一条线不续跑它继承的目标；已完成或受阻的目标停下——当前对照候选（§8）。

### 9.6 ContextCompaction

**所有者：** ContextCompaction；在 [#554](https://github.com/arcships/dim/issues/554) 下实现。

- **声明的部件**以 [压缩需求 §7.1](compaction-quality.md#71-contextcompaction) 为准，它载有 [§3](compaction-quality.md#3-压缩保住什么) 要求的各个部件，已在 [#528](https://github.com/arcships/dim/issues/528) 下实现：摘要提示词用自己的措辞声明它们，实质摘要检查验证它们在场（[ContextCompaction §5.2](plugins/ContextCompaction.md#52-productsummarystrategy)）。
- **语言。** 提示词是英文，它要求的摘要保持会话的语言、标识符逐字保留（§7）。
- **策略。** 提示词与长度指令是策略：改动用 `summary-eval --candidate` 评估（§8.2）。
- **指南。** 它写的每个标记都有条目：摘要信封、`[input <id>]` 句柄、清单消息（§6.2、§9.2）。

### 9.7 Loop 与 ContextPreparation

**所有者：** Loop 与 ContextPreparation；在 [#555](https://github.com/arcships/dim/issues/555) 下实现。

- **不自己组装指南。** ContextPreparation 发布供采用的 System，也就是 Prompt 组合好的那份，指南与条目都在其中；Loop 承载它所组装请求的 System。两者都不追加那份固定文字或任何条目。
- **今天带着指南的请求仍然带着它**：由采用配置构建的请求带着它所属 Session 采用的指南，摘要请求也包括在内；宿主准备的路径带着同一份组合，今天由它送达的条目一样不少（§6.2）。
- **没有条目让缓存前缀分叉。** 请求从不自己组装指南；条目在写入者装载或卸载处出现，两条路径都一样（§5 第 3 条、§6.2）。

### 9.8 评估工具

**所有者：** 评估工具，`xtask`；在 [#550](https://github.com/arcships/dim/issues/550) 下实现。

- **一个场景运行器**，带 §8.1 的候选注入与检验：场景即用例，两臂都跑 shipped 装配，结果写进 PR。它逐次交错两臂，并接受 `--jobs` 与重复的 `--text`/`--candidate` 对，因此一个跨同一所有者两段文本的改动按它本来就是的一次改动来判定（Goal §A.5.2）。
- **已完成评估的运行可以重判，也可以合并报告。** `--rejudge DIR` 按这些运行保存的视图重新判定，不产生模型轮次，保留每次运行自身的结局，写入新的 `--out`；`--pool DIR` 把一次已完成评估的运行加入报告，该参数可以重复给出，从而把多次已完成评估的运行按同一规则与同一格式一起报告，不写入其中任何一个，而解析后落在某个来源内部的 `--out`（经由 `..` 或链接）会在创建任何东西之前被拒绝。这样的报告会列出它的来源，没有 text 行与 candidate-token 行；合并报告里的 model 与 judge 两行是收到的参数，每个来源自己的报告才写着它的运行是凭什么判的。这样的报告还会给出再次发送 decline 的次数，以及有多少运行没有记录该次数。
- **不用绝对通过线，不进 CI**（§8.1）。
