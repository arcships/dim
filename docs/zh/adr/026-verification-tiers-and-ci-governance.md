# 026: 验证分层、测试覆盖与 CI 治理原则

决策状态：Proposed（提案）。

## 背景

每当主干出现回归或新增一种检查手段，如果习惯性地把它直接挂进 PR 必跑门禁，仓库的验证体系就会单调膨胀。时间一长，两个本应分开的概念会被混为一谈：

- **仓库的验证覆盖面**：仓库维护的全部检查、形式化模型、测试套件、基准评估与发布验收手段。
- **活跃 PR 门禁**：每次合入前必须同步跑完的有界子集。

一旦把两者画上等号，慢速集成测试、跨平台检查、为测试而触发的重复编译以及脆弱的文本扫描就会全部堆在同一条门禁里。耗时逼近上限时，靠调大超时阈值只会掩盖退化，最终演变为长队列等待、编译缓存写爆淘汰、任务相互取消，反过来同时伤害开发反馈速度与 `main` 主干信号质量。

## 决策

### D1. 测试按执行角色分为三态，验证分层（L0–L4）映射到对应状态

每项验证资产必须明确其执行态，以决定生命周期与 CI 成本归属：

1. **活跃门禁（Active Gate）**：PR 每次自动运行并受明确耗时预算约束，守卫高频契约与受影响依赖闭包。
2. **保留按需（Retained / On-demand & Sweep）**：保留在仓库中，**不阻塞日常 PR**；在资产自身文件变动（如形式化模型编辑）、定时全量扫、发版前、排障复现或设计/协议评审要求时拉起，各层级的具体触发条件以下表「默认执行态与触发方式」列为准。保留的 Rust 测试继续参与编译检查（例如聚合后标注 `#[ignore]`）以防编译腐烂；依赖外部工具链的检查（TLC/Java、本地 tmux E2E、独立性能脚本）不绑入日常构建链。
3. **开发调试（Dev / Exploratory）**：开发或排障期间编写的临时探针与细粒度局部测试。合入前必须消融：具持久契约价值的进入活跃门禁（D3），具长期复现诊断价值的转为保留按需，其余随分支清理，不入主干长期背债。

五层验证资产（L0–L4）的默认执行态与触发方式如下：

| 层级 | 守卫的核心问题 | 范围 | 默认执行态与触发方式 |
| --- | --- | --- | --- |
| **L0 — 设计与形式化层** | 抽象状态机、协议与交接不变量本身是否存在反例？ | 形式化模型（如 TLA+ 规约及 `.cfg` 性质） | **保留按需**：(a) 修改形式化模型文件时触发（若接入 CI 须按 D4 披露工具链成本）；(b) 当实现改动影响已建模的交接、恢复或先后序承诺时，通过 PR 清单与评审强制触发。普通实现 PR **不跑**。 |
| **L1 — 静态形式与契约层** | 格式、依赖边界、ADR 不可变形式、公开 schema / wire 类型及依赖合规是否破坏？ | 格式化、Lint、纯静态形式/结构检查（含每个 PR / ADR 变动必跑的 ADR 冻结检查）、前端类型检查/Lint、源码静态提取的 wire/schema 契约、依赖漏洞与许可证扫描 | **活跃门禁**：每个 PR 最快失败门禁，按改动面精准触发（依赖合规仅在 manifest、lockfile 或策略文件变更时跑）。 |
| **L2 — 业务流层** | 改动模块及其传递下游的业务行为契约是否保持正确？ | 单元测试与进程内或 loopback 流程测试（以及须编译 workspace 才能运行的运行时装配结构校验） | **活跃门禁**：在主力高吞吐平台运行改动 crate 的**反向依赖闭包**（公共底层 crate 或全局构建配置改动时扩大至全 workspace）。重型历史、长时压测或低频流程归入**保留按需**。 |
| **L3 — 真实环境与跨平台层** | 真实 OS 原语、真实进程/插件接线、终端交互与外部协议边界是否正常？ | 平台专属边界窄集、真实 daemon + 插件运行时流、交互式终端 E2E、外部注册表验收 | **拆档**：仅触及平台/客户端代码时，极窄的 OS 专属原语边界进**活跃门禁**；全量跨平台与外部注册表验收归**保留按需**（`main` 异步/定时扫、发版前或按需）；交互式终端 E2E 归**保留按需（仅限本地）**——只在本地按需或发版前运行，**绝不**由任何 CI workflow 触发。 |
| **L4 — 效果、性能与发布层** | 模型效果、资源预算、可执行文件布局或分发包是否退化？ | 评测套件（eval）、内存/启动测量、原生代码布局构建、多平台发布包构建与注册表/镜像验收 | **执行始终归保留按需**（仅定时、手动或发版流程，绝不阻塞普通功能 PR）；修改 L4 工具链自身时，该工具自身的 L1/L2 自检作为**活跃门禁**在其 PR 上运行。 |

形式化模型（L0）验证的是「抽象状态机在有限状态空间内满足安全性与条件活性」，不是代码编译检查。普通代码改动依靠 L2 流程测试守住「实现依然精化模型动作」；若实现改动改变了模型假设的交接或先后序承诺，本质上属于设计变更，须通过评审回到 L0 更新并重跑模型后再合入。

### D2. 文档承担引导与语义约束；自动化检查只控形式与结构边界，不控内容语义

文档的职责是引导贡献者并陈述语义契约。针对文档和源码约定的自动化检查只应约束**确定性、低误报的形式与结构不变量**：

- **纯静态形式检查（L1，零业务编译）**：生命周期与不可变形式（如已接受 ADR 冻结检查）、链接与模板结构完整性，以及基于 manifest 或 AST 的静态结构校验（如 crate/模块依赖边界、源码解析的类型声明），既不编译业务运行时 crate，也不解析自然语言散文。
- **需组装运行时的结构投影（随 L2 编译路径）**：固有需要编译并装配运行时才能计算的确定性「代码到文档」投影（如实时公开服务目录）归入依赖 workspace 编译的校验路径，不阻塞纯文档、前端或脚本 PR。
- **克制入库自动生成文件**：只有当生成文件被下游代码直接消费（如跨语言类型声明），或是精简且被文档实际引用的公开摘要时，才应提交进 Git 并做过期校验；纯用于依赖边界校验的细粒度内部图谱应在内存中实时检查、本地按需生成，不提交进 Git 制造合并冲突。
- **不以自动化测试强控**：文档散文的语义正确性、设计优劣，以及“某次实现改动是否触及已建模不变量”这类语义判断。避免新增试图从源码字面量推断语义、依赖不断膨胀的人工白名单维系的跨语言文本扫描（既有白名单扫描器仅过渡保留至被类型、边界或行为测试替代，不再效仿）；语义约束通过类型系统、模块边界、评审清单、L0 模型与 L2 行为测试保障。

### D3. 测试覆盖遵循最低流程/契约层、单一归属、生产不可达注入与产物治理

测试质量取决于单位成本下对契约的保护力，而不是在最高层堆积用例数量：

- **能证明契约的最低流程层或契约层**：关于私有模块、helper 或单个函数的断言应落在最近的流程测试或契约测试中，不鼓励为内部实现写孤立单测；同时状态转换、渲染规则、参数校验与错误矩阵不得写成起真实进程、PTY 或拷贝二进制的端到端测试。E2E 只覆盖代表性接线与真实 OS 交互路径，不做排列组合穷举。
- **单一归属原则**：下层（或专用套件，如本地终端 E2E）已证明的行为，上层仅验证链路接通，不重复异常矩阵。覆盖迁移到更合适的载体后，须在同一改动或对应迁移任务中同步退役或降级原活跃 CI 用例。
- **生产安全的运行期注入替代重编译**：测试态差异（release 标记、build ID、时钟、端点、故障注入）应在运行期或测试边界注入，避免通过切换编译期环境变量迫使 CI 级联重编上游 crate。**生产安全红线**：所有仅用于测试的覆写入口**在 release 构建中必须不可达**（仅在 debug/test 构建编译），或严格限定在测试夹具入口内，绝不扩大生产二进制可接受的外部输入面。
- **把测试二进制当作工程产物治理**：按 crate 将集成测试聚合为少量均衡的入口二进制，避免大量单文件测试可执行文件重复全图链接、放大编译缓存写盘体积；同时拆分过大的单一测试二进制，消除单进程调度长尾与链接器压力。

### D4. 活跃门禁实行有记录预算制与轻重物理隔离

- **有记录的耗时与资源预算**：每个同步活跃门禁层声明明确的耗时与资源预算（随 runner 实测数据记录在 `docs/architecture/build.md` 与追踪 issue 中，不在不可变 ADR 内写死具体分钟数）。逼近或触发预算上限视为退化，须通过收敛范围、优化慢测、提升并行度或降级到保留按需来压回预算，**禁止**以单纯调大作业或单目标超时作为解决方案。
- **门禁增量成本显式化**：任何向 PR 必跑门禁新增检查或扩大路径匹配规则的变更，必须写明增量耗时、新增编译依赖与目标 runner 池。
- **轻量检查与重型构建物理隔离**：纯静态仓库检查不得依赖编译业务运行时 crate。文档、前端、脚本与静态检查运行在轻量作业中，不得抢占重型编译或稀缺平台 runner 池。

### D5. 影响面路由与稀缺平台最小化，以定时全量扫和周期减法为前提

- **影响面路由与全量扫前置条件**：PR 与 `main` 推送均按改动路径选择检查组，且 `main` 推送各自独立跑完、不相互取消。**只有在定时全量扫已上线运行时，才允许收窄 `main` 推送**，以兜底跨组隐式耦合；全量扫失败须有明确的分诊归属与针对区间合并提交的二分定位流程。
- **显式路径分类**：新增顶层目录或非代码资产时，必须在路径路由器中显式归类，不得静默落入最昂贵的全量兜底组。
- **稀缺平台仅验证平台专属边界**：全量编译与平台无关的 L1/L2 验证集中在高吞吐主力平台（Linux）。稀缺 OS 池（macOS、Windows）在 PR 阶段仅运行触及平台专属代码路径（`cfg(target_os = ...)`）、原生 OS API 或目标打包边界的检查，且专属清单应由源码机制核对，不依赖易漂移的人工白名单。
- **周期性可观测与减法维护**：定期复盘 CI 指标（排队 p90、执行 p90、缓存写入/淘汰体积、最慢测试目标、0 匹配死步骤与取消浪费率），持续淘汰过时检查并将新长尾降级至保留按需。

## 影响

- 新增测试、静态检查或形式化模型接入 CI 前，须先明确其执行态（活跃/保留/调试）、层级（L0–L4）与归属。
- 在本 ADR 被正式接受且配套工具变更落地前，`AGENTS.md` 与 `docs/architecture/` 仍是现行命令与入库快照的权威依据；对齐后可将 `AGENTS.md`（`## Testing`）的测试规则统一收口指向本决策以避免重复。
- 纯静态形式检查与依赖全后端的研发工具解耦，保持文档、前端与脚本 PR 的快速反馈。
- 仅服务于测试的编译期开关改为生产不可达的运行期/夹具注入，消除级联重编且不放松生产安全边界。
- 具体 workflow 调整、runner 迁移、定时全量扫、测试二进制聚合与具体预算数值均落在 `docs/architecture/build.md`、`docs/release/README.md` 与追踪 issue 中。

## 非目标

- 降低仓库整体缺陷检出能力，或在没有合适层级或执行态替代覆盖的情况下删除测试。
- 在不可变 ADR 中写死具体分钟数阈值、runner 主机名、workflow 语法或逐 crate 路由表。
- 用自动化检查替代设计评审与代码审查。

## 替代关系

不替代任何既有 ADR。本决策承接 [ADR 008](../../adr/008-documentation-ownership.md) 的分层边界：本文件仅定义验证与 CI 治理原则，预算数值与当前 CI 实现留在 `docs/architecture/build.md` 与 `docs/release/README.md`，推进状态留在 issues。
