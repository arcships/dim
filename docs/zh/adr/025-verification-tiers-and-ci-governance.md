# 025: 验证分层、测试覆盖与 CI 治理原则

决策状态：Proposed（提案）。

## 背景

每当主干出现回归或新增一种检查手段，如果习惯性地把它直接挂进 PR 必跑门禁，仓库的验证体系就会单调膨胀。时间一长，两个本应分开的概念会被混为一谈：

- **仓库的验证覆盖面**：仓库维护的全部检查、形式化模型、测试套件、基准评估与发布验收手段。
- **PR 门禁的执行面**：每次合入前必须同步跑完的有界子集。

一旦把两者画上等号，慢速集成测试、跨平台检查、为测试而触发的重复编译以及纯静态扫描就会全部堆在同一条串行门禁里。耗时逼近上限时，如果只靠不断调大超时时间来兜底，真正的问题会被掩盖，最终演变为长队列等待、编译缓存写爆淘汰、任务相互取消，反过来同时伤害开发反馈速度与 `main` 主干信号质量。

## 决策

### D1. 按变动性质与反馈周期将验证分为五层（L0–L4）

所有验证资产按「守卫的问题类型、触发条件、预期反馈周期」归入五层，各司其职，不再平铺混跑：

| 层级 | 守卫的核心问题 | 范围 | 触发时机 |
| --- | --- | --- | --- |
| **L0 — 设计与形式化层** | 抽象状态机、协议与交接不变量本身是否存在反例？ | 形式化模型（如 TLA+ 规约及 `.cfg` 性质）、ADR 不可变检查 | **仅设计/契约变动时触发**：当形式化模型、协议/事件契约、恢复边界或交接不变量变更时运行；普通实现 PR **不跑**。 |
| **L1 — 静态与契约层** | 格式、依赖边界、公开 schema / wire 类型、静态源码规则及依赖合规是否破坏？ | 格式化、Lint、纯静态仓库扫描、前端类型检查/Lint、wire/schema 契约、依赖漏洞与许可证扫描 | **每次 PR 按改动面精准触发**（依赖合规仅在 manifest、lockfile 或策略文件变更时跑），作为最快失败门禁。 |
| **L2 — 影响面业务流层** | 改动模块及其直接下游的业务行为契约是否保持正确？ | 受影响 crate 及直接下游的单元测试、进程内或 loopback 流程测试 | **每次 PR 在主力高吞吐平台运行**；仅在公共底层 crate 或全局构建配置改动时扩大至全 workspace。 |
| **L3 — 真实环境与跨平台层** | 真实 OS 原语、真实进程/插件接线、终端交互与外部协议边界是否正常？ | 平台专属边界窄集、真实 daemon + 插件运行时流、交互式终端 E2E、外部注册表验收 | **按成本拆分**：仅触及平台/客户端代码时在 PR 跑对应的 OS 专属窄集；全量跨平台与外部注册表检查在 `main` 异步或定时运行；交互式终端 E2E 在本地按需及发版前运行。 |
| **L4 — 效果、性能与发布层** | 模型效果、资源预算、可执行文件布局或分发包是否退化？ | 评测套件（eval）、内存/启动测量、原生代码布局构建、多平台发布包构建与注册表/镜像验收 | **仅定时（Nightly）、手动触发或发版流程运行**，绝不阻塞普通功能 PR。 |

形式化模型（L0）验证的是「抽象状态机在有限状态空间内满足安全性与条件活性」，不是代码编译检查。普通代码改动依靠 L2 流程测试守住「实现依然精化模型动作」。如果某次实现修改破坏了模型假设的交接或先后序承诺，它本质上属于设计变更，必须回到 L0 更新并重跑模型后再合入。

### D2. 测试覆盖遵循「最低层证明、单一归属、运行期注入、产物治理」四条规则

测试质量取决于单位成本下对契约的保护力，而不是在最高层堆积用例数量：

- **最低层证明原则**：纯逻辑、状态转换、渲染规则、参数校验与错误分支矩阵必须下沉到组件、状态机或进程内流程测试，禁止写成起真实进程、PTY 或拷贝二进制的端到端测试。E2E 套件只覆盖跨进程接线与真实 OS 交互的代表性路径，不做排列组合穷举。
- **单一归属原则**：同一行为只在一个最合适的层级做完整覆盖，上层仅验证链路接通，不重复下层的异常矩阵。当行为迁移到更合适的载体（例如组件测试或本地终端 E2E 套件）后，必须在同一改动或对应迁移任务中同步退役旧 CI 用例。
- **运行期边界注入替代重编译**：测试所需的构建态差异（如 release 标记、build ID、时钟、外部端点、故障注入）应在二进制或测试边界支持运行期注入，禁止为了测试几个分支而切换编译环境变量、迫使 CI 重编上游依赖图。
- **把测试二进制当作工程产物治理**：按 crate 将集成测试聚合为少量均衡的入口二进制，避免大量单文件测试可执行文件重复全图链接、写爆编译缓存；同时对过大的单一测试二进制做均衡拆分，避免形成单进程调度长尾或链接器压力。

### D3. CI 门禁实行硬预算制与轻重物理隔离

- **明确耗时与资源预算**：每个同步门禁层设定清晰上限（目标：L1 ≤ 2 分钟；PR 端到端中位 ≤ 8 分钟、p90 ≤ 15 分钟；OS 专属 PR 窄集 ≤ 3 分钟）。逼近或触发超时视为需要修复的工程退化，必须通过收敛范围、优化慢测、提升并行度或调整分层来压回预算内，**禁止**以单纯调大超时阈值作为解决方案。
- **门禁增量成本显式化**：任何向 PR 必跑门禁新增检查或扩大路径匹配规则的变更，必须写明增量耗时、新增编译依赖及落入的 runner 池。
- **轻量静态检查与重型构建物理隔离**：纯静态仓库检查（依赖边界、链接、字面量、打包元数据等）不得依赖编译业务运行时 crate。文档、前端、脚本与纯静态检查运行在轻量作业中，不得抢占重型编译或稀缺平台 runner 池。

### D4. 默认按影响面路由，由定时全量兜底

- **PR 与 `main` 保持一致的影响面路由**：PR 与 `main` 推送均只运行受改动路径影响的检查组。`main` 推送各自独立跑完、不相互取消，既保证每次合入都有真实的绿/红结果，又避免前端或非后端合入拖垮后端 runner。
- **定时全量兜底跨模块隐式耦合**：通过周期性定时运行（Nightly）及发版前全量门禁覆盖全 workspace 与全平台矩阵，防止跨模块隐式依赖退化漏网。
- **显式路径分类**：新增顶层目录或非代码资产时，必须在路径路由规则中显式归类，不得静默落入最昂贵的全量兜底组。

### D5. 稀缺平台仅验证平台专属边界，且定期度量和做减法

- **平台无关验证集中在主力高吞吐平台**：全量编译及平台无关的 L1/L2 验证集中在高并发、低排队的单一主平台（Linux）执行。
- **稀缺平台窄集且由代码核对**：稀缺 OS runner 池（macOS、Windows）在 PR 阶段仅运行触及平台专属代码路径（`cfg(target_os = ...)`）、原生 OS API 或目标打包边界的检查；专属清单应通过代码属性或静态检查核对，不依赖易漂移的人工白名单。
- **周期性可观测与减法维护**：定期复盘 CI 指标（排队 p90、执行 p90、缓存写入/淘汰体积、Top 最慢测试目标、0 匹配死步骤与取消浪费率），持续淘汰过时检查并治理新增慢测长尾。

## 影响

- 新增测试、静态扫描或形式化模型时，需先明确其所属层级（L0–L4）与归属，再决定是否接入 PR 门禁。
- 纯静态检查将与依赖全后端的研发工具解耦，保持文档、前端与脚本类 PR 的秒级/分钟级反馈。
- 仅服务于测试的编译期开关将改为边界/运行期注入，消除 CI 中的级联重编。
- 测试二进制形态与编译缓存体积成为与业务代码同等重要的工程审查对象。
- 具体的 workflow 调整、runner 迁移、测试二进制合并与慢测治理分别在独立实现 issue 中跟踪，不写入本 ADR。

## 非目标

- 降低仓库整体缺陷检出能力，或在没有合适层级替代覆盖的情况下删除测试。
- 规定具体的 CI 平台语法、runner 主机名或逐 crate 路径表（这些属于 workflow 文件、架构文档与 issue 范畴）。
- 用自动化检查替代设计评审与代码审查。
