# Badcase 评测流水线：从真实失败到回归题

Related: [#1701](https://github.com/arcships/dim/issues/1701)（usercases 语料）。交付状态在 issue，不在本文。

## 目的与范围

usercases 语料回答「这次改动有没有把用户真实踩过的坑重新挖开」。语料本身只是流水线的中段。
本文定义它的前后两段，以及各段之间交接什么：**一个真实失败怎样被收进来、怎样决定它该变成
哪种测试、怎样证明做出来的题确实在测那个失败、跑完之后怎样读结果并回到修复。**

来源是三个：**用户主动提交、内部 dogfood、公开 issue。** 前两个带真实材料，是这条流水线存在的
理由；第三个没有授权负担，用来先把后半段跑通。不扫描、不默认上传任何会话。

| 范围 | 是否纳入 | 所有者 |
|---|---:|---|
| 各阶段的输入、产物、准入条件与交接 | 是 | 本文 |
| 证据包的内容、授权范围、存放与撤回 | 是 | 本文 |
| Timeline 进证据包之前在本机怎样取舍、替换和校验 | 否 | [证据包打包](evidence-pack.md) |
| 根案例的身份，以及按根案例读结果的规则 | 是 | 本文 |
| 结果到 issue 的闭环动作 | 是 | 本文 |
| 任务格式、判分语义、成对规则、pin | 否 | [usercases 语料合同](../../benchmarks/usercases/README.md)（#1701） |
| 触发、k 的语义、门禁是否阻断 | 否 | [trigger-policy.md](trigger-policy.md) |
| 运行入口、结果有效性、baseline 与配对比较 | 否 | [benchmarks/README.md](../../benchmarks/README.md) |
| `/report` 里能带什么证据 | 否 | [Report 插件](../design/plugins/Report.md) |
| Timeline 导出的格式、内容与敏感性 | 否 | [Timeline export](../design/appserver/timeline-export.md) |
| 缺陷修复自带的 flow test 怎么写 | 否 | [AGENTS.md](../../AGENTS.md) Testing |

本文依赖语料合同里的三项：manifest 的 `source_issue` 与 `kind`，以及主任务与对照成对入集的
规则；该合同变化时本文跟随，不另行定义。

本文不涉及插件、Capability、事件或核心机制，也不改 Timeline 导出格式或 Report 插件；设计规则
§4 与 ADR 002 不适用。

   ├──────────────► 产品 flow test，随修复 PR（需要中断、重启、时序）   ║
   ▼                                                                    ║

   ▼                                                                    ║

   ▼                                                                    ║

   ▼                                                                    ║
 分析：按根案例成对读结果 × issue 状态                         §分析   ║
   ▼                                                                    ║

本文新增的是：证据包与授权的合同、分诊去向规则、区分度证明、按根案例的读法、闭环与撤回动作。
其余阶段由已有的合同承载，本文只给链接。

## 根案例是一个跟踪 issue

一个根案例对应本仓库的一个 issue。语料 manifest 里每道题的 `source_issue` 就是它的根案例键，
主任务和对照共用同一个键。

| 来源 | 跟踪 issue 是什么 |
|---|---|
| 公开 issue | 原 issue 本身 |
| 内部 dogfood、用户主动提交 | 新开的 issue，只写可公开的内容：一句不含用户材料的症状、机制类别、Dim 版本、证据包编号 |

本仓库是公开的，所以带真实材料的根案例在 issue 里只留一个壳：会话 ID、用户身份、对话与文件
内容都不出现在里面。证据包编号是随机生成的，不从账号、会话或内容派生。

这样定的后果是有意的：

- 不另设登记表或状态机。分诊结论、修复状态都写在 issue 里，仓库的惯例本来就是「状态在 issue」。
- 回归题和能力题不需要字段区分：issue 已关闭的是回归题，仍打开的是能力题，读法见 §分析。
- 一个根案例可以同时有 usercases 题和 flow test，它们是同一个案例的两种证据，统计时只算一个
  根案例。

待进入流水线的 issue 用一个标签标出（建议 `eval-badcase`，尚不存在）；流水线发现的失败沿用
已有的 `eval-failures`。

## 收集

### 三个来源

| 来源 | 复现材料 | 原始材料在哪 | 谁做构建 |
|---|---|---|---|
| 用户主动提交 | 证据包 | 经授权后私有接收 | 有权访问该证据包的人 |
| 内部 dogfood | 证据包 | 不离开报告人本机 | 报告人本人 |
| 公开 issue | [缺陷报告模板](../../.github/ISSUE_TEMPLATE/01-bug-report.yml)里的最简复现 | issue | 任何贡献者 |

三种来源都可以用 [`/report`](../design/plugins/Report.md#6-preview-and-sharing) 反馈。报告默认只含诊断信息。只有发送人勾选附带对话，当前会话报告才会加入近期用户和助手的片段。脱敏默认开启；关闭脱敏不会自动附带对话。分享前要查看预览。GitHub 草稿和 Discord 的自动摘要不含对话，不代表 ZIP 可以公开。

普通反馈到此即可，不要求导出 Timeline。邮件默认只允许排查本次问题。只有发送人明确选择团队内部回归评测，且收件人核对邮件里的 SHA-256 与附件一致时，才可按此范围使用**这份报告**。附件不符、授权缺失或措辞含混时，不作评测。这个选项不授权把内容发给外部模型供应商，不允许训练或公开，也不是完整证据包的接收入口。材料不足就向报告人说明缺什么，不从会话里自动补采。

### 提交

以下步骤只用于报告不足、需要进一步提交证据包的案例。普通报告的邮件流程不要求再开 issue、再做一份 ZIP，也不调用 Timeline 打包器。

1. 在出问题的 Session 里运行 `/report`，用它的 issue 草稿建跟踪 issue。
2. 选定失败锚点：`/report` 里的事件序号，或整个任务。
3. 写两句话：哪里不对；怎样才算做对。它们可能带用户材料，所以进证据包，不进 issue。
4. 导出这个 Session 的 Timeline，在本机[打包](evidence-pack.md)。默认只带事件的结构和双方的
   对话文字；提交人读完将要带走的全部内容，可以删减。工具输出、思考和文件不在默认范围里，
   构建人需要时按编号点名，提交人逐个放行。
5. 逐项给出授权（见下）。
6. 拿到证据包编号，凭它查询处理进度或撤回。

自己做构建的 dogfood 报告人跳过第 4 步：材料不离开他的机器。只提交文字、不给任何材料也可以。
这样的提交停在 issue，成不了可运行的题。

### 证据包

| 内容 | 必需 |
|---|---|
| 哪里不对、怎样才算做对、失败锚点 | 是 |
| Dim 版本、模型身份、权限模式、启用的插件 | 是 |
| 授权记录 | 是 |
| Timeline：`dimcode export` 的输出经[打包](evidence-pack.md)之后的包 | 由别人分诊或构建时 |
| 失败**之前**的输入文件与工作区状态 | 要做成可运行的题时 |
| 外部依赖的冻结副本：题目用到的网页或 API 响应 | 题目依赖它们时 |

Timeline 导出不是可运行的环境：它没有文件快照，也没有外部服务的状态。只有失败之后的文件
通常恢复不出原题，所以工作区状态要单独提供。模型的思考过程不是必填项，判分也不依赖它。

证据包永不包含：provider 凭据、`.env`、SSH 私钥、cookie、浏览器 profile、整个 home 或整个
工作区、生产账号的登录态。导出按合同不读凭据表，但用户或工具写进对话里的密钥会原样出现在
Timeline 中。

原始导出不在证据包里，始终留在提交人本机。证据包里的 Timeline 是打包之后的：默认省略内容、
替换标识、校验不过就不产出，规则见[证据包打包](evidence-pack.md)。打包之后的包仍是敏感材料，
下面的授权与存放照样适用。

### 授权

三项范围分开给出、分开记录，缺一项就不做那一项对应的事：

| 范围 | 允许什么 |
|---|---|
| 诊断 | 用证据包分析这一次失败 |
| 回归集 | 脱敏后的派生材料进入长期保留的私有语料 |
| 模型供应商 | 派生材料随评测运行发送给被测模型的供应商，失败 trial 的片段发送给失败分析所用的模型 |

第三项是必需的而不是附带的：运行一道题就是把它的 fixture 发给模型，
[analyze.py](../../benchmarks/report/analyze.py) 归类失败时会把题面、判分器输出和 Timeline
末段发给另一个模型。

任何一项授权都不包含：模型训练、公开发布、原始证据包的长期保存。

授权记录只有证据包编号、给出的范围、日期、到期时间和脱敏版本。提交人的身份映射与它分开
保存，只有分诊者可见；跟踪 issue 里只出现证据包编号。团队或企业工作区的提交还要满足管理员
策略，并由提交人确认自己有权分享其中的材料。

### 存放

| 资产 | 存放 | 删除 |
|---|---|---|
| 原始证据包 | dogfood：报告人本机。用户提交：私有、可删除、访问有审计的存储 | 到期或撤回时删除 |
| 派生 fixture | 语料任务树，在私有仓库里 | 从任务树移除并升 pin |
| 授权记录、身份映射 | 与原始证据包同一存储，彼此分开 | 撤回后只留不含内容的删除记录 |
| 跟踪 issue | 本仓库，只有可公开的内容 | 不需要 |

原始证据包不进任何 git 仓库、issue、CI 产物或日志。

### 接收用户提交的前置条件

以下各项定案之前，不开放用户提交的私有接收：

- 原始证据包存放在哪，谁能访问；
- 保留期限与撤回后的删除时限，包括备份；
- 派生 fixture 撤回后，私有仓库 git 历史里的副本怎样处理。这一条必须在授权时向提交人说明；
- 允许使用哪些模型供应商。

这些由产品与隐私负责人决定（见 §向所有者提出的需求）。定案之前，用户仍可以通过公开 issue
提交不含隐私的最小复现。dogfood 不受此限：原始证据包不离开报告人本机，给出授权的就是报告人本人，
进入私有语料的只有他审过的派生 fixture。

首版用专用企业邮箱作为唯一的私有提交入口，不另做上传页。邮箱通过验收且上述条件全部满足后，
才接收提交人在本机审阅确认、为本次排查所必需的脱敏证据包。不接收原始会话导出、凭据或本机
审阅文件。收件人核对已确认的 `pack.json`、其中记录的 `timeline.jsonl` 摘要、授权范围和到期日，再按证据包编号发回执。打包器确认的不是外层 ZIP；同一封邮件里另附的失败说明、工作区文件或外部依赖，不继承这份授权。未经单独审阅并绑定授权的旁附材料，不接收、不复用。提交人可回复邮件，凭编号申请撤回。

开放前，邮箱管理员和隐私负责人用合成包验证：只有指定收件人能访问（获准与未获准账号各测一次），
有可查询的访问记录，能按编号受理撤回。确认到期或撤回后邮件、归档和备份各自的删除时限；
验收前不接收真实证据包。用合成附件检查三种拒绝情况：普通报告摘要相符但未选内部回归，不作评测；选了内部回归但 ZIP 摘要不符，也不作评测；已确认的证据包附带其他文件，不把包的授权延伸给旁附文件。

## 分诊

分诊回答四个问题，结论写在跟踪 issue 里，写法不带用户材料。

**一、材料能不能用。** 带证据包的来源先核对授权是否仍有效，再按用途分别判断：只有授权诊断才
能用包排查；只有授权回归集且列出允许的模型供应商才能用派生材料做题；评测和失败分析也只能把材料
发给获准的供应商。缺少某项授权就不做该项，不以另一项代替。公开 issue 跳过这一问。

**二、它是不是一个可用的案例。** 以下任一项不成立就留在 issue，不进入后续阶段，也不进任何
分母：失败有证据；预期结果能写成一句不依赖解题路线的话；失败能在一个干净环境里重新出现，偶发
的要写明出现次数。

用户不满意不等于 harness 有缺陷。分诊不要求给出根因，根因不明的案例照样可以入题，只要失败
可复现、预期可判分。

**三、它与已有根案例是否同源。** 同源就并到已有 issue，不另立案例。

**四、它该变成哪种测试。** 按可表达性选去向，不按重要程度：

| 复现这个失败需要什么 | 去向 |
|---|---|
| 一次 `dimcode exec` 能在容器里跑完，终态能被确定性判分 | usercases 题：主任务 + 对照 |
| 进程被杀后重启、取消与完成竞争、通知乱序等时序，且用固定的模型输出就能驱动 | 产品 flow test，随修复 PR 合入；不入语料 |
| 真模型 + 多轮输入、中途 steer 或外部事件 | 目前没有承载，见 §开放问题 |

第二行不入语料的原因是适配器每个 trial 只运行一次 `dimcode exec`，注入不了中断。这类案例由
确定性的 flow test 保护更便宜也更准，它是普通的 CI 测试，不产生通过率，本文也不为它另设
统计。flow test 在本仓库里是公开的，所以它的 fixture 只能是合成材料。

## 构建

任务格式、成对规则和判分语义以语料合同为准。本节规定从材料到题目之间必须做到的三件事，
结论写在入集 PR 里。

**初始状态是失败之前的状态。** 题目从用户开始这件事时的工作区出发，不从失败之后的现场出发，
也不把用户后来用来纠错的话写进题面。最小化可以删掉与触发无关的内容，但要保留触发条件本身。

**fixture 重写，不照搬；替换不能改掉触发条件。** 来自证据包的 fixture：

- 题面和工作区由构建人重写或合成，用来复现触发条件，不从证据包里照搬原文。只有触发条件
  依赖原文时才保留那一段。这让进入语料的内容经过第二个人，不依赖提交人打包时没有漏。
- 重复出现的名称、路径、数值用一致的占位符替换；失败所依赖的长度、相对关系、单位和边界条件
  保持不变。压缩类案例需要等长的替代材料，而不是把上下文删短。
- 任务名与本仓库 manifest 里的任何字段不带用户材料。
- 提交的脚本、文件和网页一律视为不可信：构建时不在沙箱之外执行它们，任务容器里没有生产
  凭据。

**区分度证明。** 一道回归题如果在修复前和修复后都通过，它什么也没测。入集前在修复 PR 的父提交
上运行这一对题，期望结果是主任务失败、对照通过。证明跑的是脱敏之后、准备入集的那份 fixture，
所以它同时回答了「脱敏有没有把缺陷一起修掉」。

| 修复前的结果 | 结论 |
|---|---|
| 主任务失败，对照通过 | 题目复现了根案例，可以入集 |
| 主任务通过 | 题目没有触发这个失败，回到最小化或脱敏 |
| 对照失败 | 失败不属于这个机制，或题目本身有缺陷，回到构建 |
| 修复前的构建无法运行 | 入集 PR 写明原因；该题的通过不得被引用为「修复仍然有效」的证据 |

能力题（issue 仍打开）在当前 main 上做同一件事：主任务失败、对照通过，才算复现。

这次测量用 `baseline` 运行类型加 `--head <提交>` 进行，它不判窗口、不推进 state。该运行类型
会写出 `<pin>.json`，所以 `--baselines-dir` 要指向临时目录，避免覆盖同一 pin 的参照；结果写在
入集 PR 里，不作为 baseline 文件提交。

## 运行

没有新的入口。运行方式、窗口语义和首次上机自检见语料合同；k=1 是 screen、k=3 才可定性，
见 [trigger-policy.md](trigger-policy.md#experiment-parameters)。

## 分析

通用的配对比较和逐 trial 的失败归类已经存在：[baseline.py](../../benchmarks/runner/baseline.py)
给出每题相对 baseline 的变化，analyze.py 把每个失败 trial 归为 `agent`、`environment`、
`timeout`、`model_api`、`harness` 或 `unknown`。本节在它们之上增加一层：**按根案例成对读。**

读法只在 k=3 的运行上有定义。k=1 的运行只回答一个问题：哪些根案例值得跑一次 k=3。未判分和
infra 失败的 trial 先按结果合同剔出；剔出后不足 k 次的那一对不读。

| 主任务 | 对照 | 读法 |
|---|---|---|
| k/k | k/k | **保持**：机制在这个构建上成立 |
| 0/k | k/k | **失败**：失败形态与根案例一致 |
| 介于两者之间 | k/k | **不稳**：记录通过次数，不下结论 |
| 任意 | 不是 k/k | **对照失效**：这一对不产生关于该机制的结论 |

对照失效时看 analyze.py 给对照题失败 trial 的类别：`environment` 或 `harness` 指向题目或评测
环境，`agent` 或 `timeout` 指向通用能力或预算。两种都不是这个根案例的回归。

读法再与 issue 状态相交，得到这次运行对这个根案例的结论：

| 读法 | issue 已关闭（回归题） | issue 仍打开（能力题） |
|---|---|---|
| 保持 | 无动作 | 修复候选 |
| 失败 | 回归 | 预期中，无动作 |
| 不稳 | 记录 | 记录 |
| 对照失效 | 查题 | 查题 |

这一层目前没有实现。它需要的输入都已存在：manifest 的 `source_issue` 与 `kind`、运行的逐题
结果、analyze.py 的输出，以及 issue 的开闭状态。建议作为 `benchmarks/report/` 下报告的一个
分节实现，不改 ledger 的记录格式。

**这不是门禁。** trigger-policy 的标定表明，同一构建上观测到 3/3 的任务下一轮仍是 3/3 的概率
约为 72%，所以单次「失败」是值得人去看的信号，不是已确认的回归。它不阻断合并。

## 闭环

| 结论 | 动作 |
|---|---|
| 回归 | 重开原 issue；原修复不再适用时新开 issue 并链接原 issue |
| 修复候选 | 在 issue 里附这次运行，由修复者确认后关闭；关闭后该题自然成为回归题 |
| 记录 | 在 issue 里记通过次数；反复出现时按随机故障讨论，不改题 |
| 查题 | 题目或判分有缺陷就改题，改题按语料合同升 pin 并重采 baseline；环境问题修环境，不改判分 |

**写进 issue 的内容随来源而定。** 公开 issue 来源的题可以附 trial 的 Timeline 末段与判分器
输出。带证据包来源的题只写任务名、通过次数、读法、失败类别和运行编号；Timeline 片段、判分器
输出和 analyze.py 引用的原文留在评测机的结果目录里，不进 issue。

题目只在它保护的行为被有意改变时退役：需求变了，修改或删除旧断言，在 PR 里说明。不因为
「一直通过」而删题，回归题的正常状态就是一直通过。

### 撤回

提交人凭证据包编号撤回。沿根案例做完以下各步才算完成：

1. 删除原始证据包，授权记录换成不含内容的删除记录。
2. 从任务树移除该根案例的题，重新生成 manifest；新 pin 按语料合同重采 baseline。
3. 删除评测机结果目录里含该题 trial 的运行产物。
4. 在跟踪 issue 上注明已撤回并关闭；issue 本来就不含用户材料，予以保留。

已发布的汇总数字不回改：baseline 与比较本来就按 pin 分开，旧 pin 的数字停留在旧 pin 上。

## Verification

- 每个来源各有一个根案例走完全程：跟踪 issue、分诊结论、区分度证明、入集、k=3 运行、按根案例
  的读法、issue 上的动作。带证据包的那两个，跟踪 issue 与入集 PR 的公开部分里找不到用户材料。
- 一个带合成材料的证据包走完撤回的四步，之后在任务树、结果目录和存储里都找不到它的内容。
- 打包的验证见[证据包打包](evidence-pack.md#verification)。
- 区分度证明的四种结果各有一个真实或构造的例子，结论与 §构建的表一致。
- 按根案例分析的验收要求：实现这一层时，须用固定的结果文件逐项验证读法表的四行与结论表的八格，不调用模型。

运行结果写在 issue 或 PR 里。

## 开放问题

- **真模型多轮案例没有承载。** [scenario-eval](../../xtask/src/scenario_eval.rs) 有隔离运行、
  脚本化的多轮输入、按时间或工具调用触发的事件和 judge，但它的两臂是同一构建上的两份策略
  文本，不是两个构建。它能否用来比较两个构建，需要它的所有者回答；在那之前这类案例留在 issue。
- **只重跑一对题的成本。** 运行入口按整棵任务树运行，没有按任务筛选。语料只有几对题时整跑
  可以接受；增大之后，区分度证明和对「失败」的 k=3 确认都需要更便宜的路径。
- **标签名**（`eval-badcase`）待仓库维护者确认。
