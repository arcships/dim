# 证据包打包：Timeline 的分级披露与脱敏

Scope: 提交人本机上的一个一次性工具，不在 daemon 里，不属于任何 Session。
Related: [#1701](https://github.com/arcships/dim/issues/1701)。交付状态在 issue，不在本文。

## 目的与范围

[Badcase 评测流水线](usercases-pipeline.md)的证据包里有一份 Timeline。原始的
[Timeline 导出](../design/appserver/timeline-export.md)含 prompt、代码和工具输出，不能原样离开
提交人的机器。本文定义导出与证据包之间的那一步：**哪些内容默认带上，哪些要提交人逐项放行，
带上的内容怎样替换标识，以及凭什么确认输出里没有不该有的东西。**

调用者是要把案例交给别人的提交人：开放之后的外部用户，以及把案例交给另一位构建人的内部
报告人。两者都要等[私有接收的前置条件](usercases-pipeline.md#接收用户提交的前置条件)定案。
自己做构建的 dogfood 报告人用不到它：原始导出不离开他的机器。

三条设计约束，后文每一节都服从它们：

1. **默认省略。** 只输出已列出的结构字段和允许保留的内容。未知字段连键一起丢弃，未知事件只保留事件外层信息。
2. **要人判断的量必须小到看得完。** 默认带上的内容由提交人一次读完；其余的按单元点名追加。
3. **输出不依赖判断全对。** 机器能检查的由工具检查，不通过就不产出；人会漏的由下游兜住
   （见 §不靠这一步保证的事）。

| 范围 | 是否纳入 | 所有者 |
|---|---:|---|
| 单元的划分、默认取舍、点名追加 | 是 | 本文 |
| 标识替换、占位格式、输出的校验 | 是 | 本文 |
| 确认时如何附上授权记录 | 是 | 本文 |
| 证据包的其余内容、授权范围、存放、撤回、上传通道 | 否 | [流水线](usercases-pipeline.md#收集) |
| 导出的行格式与内容 | 否 | [Timeline export](../design/appserver/timeline-export.md) |
| `/report` 的内容 | 否 | [Report 插件](../design/plugins/Report.md) |
| 工作区文件怎样进证据包 | 否 | [流水线](usercases-pipeline.md#证据包)；文件没有可利用的结构，只能逐个点名 |

本文不涉及插件、Capability、事件或核心机制，不改导出格式；设计规则 §4 与 ADR 002 不适用。

## 流程

```text
 dimcode export（完整，以 end 结尾）          留在本机，从不上传
        │
        ▼
 ① 划分单元：同样的字符串算一个单元，流式分片先拼接
        │
        ▼
 ② 取舍：第 1 级默认 + 决定文件里点名的单元          决定文件  ◄─┐
        │                                                         │
        ▼                                                         │
 ③ 替换：保留的单元里的标识换成占位                               │
        │                                                         │
        ▼                                                         │
 ④ 校验：任一项不过就不产出                                       │
        │                                                         │
        ├──► 审阅文件（本机）：保留的单元全文、省略的单元清单 ────┘ 提交人改决定后重跑
        ▼
 包：timeline.jsonl + pack.json + 摘要
        │  提交人确认摘要，记入授权记录
        ▼
 证据包（上传与存放见流水线）
```

打包脚本只向本机受信任的 `dimcode evidence-redact` 进程传入原文，每次打包只启动一个进程；保留内容的替换、授权里的凭据检查和输出残留检查都由它处理。运行时显式指定支持此命令的可执行文件，例如：

```sh
python3 benchmarks/usercases/pack.py EXPORT --out DIR --dimcode /absolute/path/to/dimcode
```

也可以设置 `DIM_EVIDENCE_DIMCODE` 为该文件的绝对路径。命令行参数优先；工具不从 `PATH` 或当前目录寻找程序。未指定、路径不是绝对路径或进程失败时，不会改用其他程序或 Python 规则，也不留下包。

工具不联网、不调用模型、不上传。同一份导出、同一份决定文件、同一版规则，生成的 `timeline.jsonl`
逐字节相同。清单里的 `timeline_sha256` 供收件人校验 Timeline；本机确认使用完整待发送清单的
SHA-256。清单已包含 Timeline 的摘要，所以确认时两份文件都不能变。这个摘要不是签名，不证明
提交人身份。

## 单元

工具按事件种类列出允许输出的字段及类型。**未列出的键和值一起省略**，不因值是数字、布尔值或
对象而保留；未列出的事件只带事件外层信息，不带原始事件正文。

| 已列出的字段 | 例子 | 处理 |
|---|---|---|
| 结构 | 事件名称、序号、关联 ID、状态、模型 ID、计量数字 | 保留结构；按替换规则处理标识 |
| 不可读 | 供应商的签名、加密内容及无法审阅的推理数据 | 用固定占位替换，不允许放行 |
| 内容 | 对话、工具参数和结果、before trace、自由文本错误原因 | 划成单元，按 §分级 取舍 |

字段是不是内容由协议定义，不由某个样例的取值决定。例如回合结束的 `reason` 即使写着
`end_turn`，仍按自由文本处理。新增字段在列入允许清单前不会进入输出。

**单元按内容相等划分。** 同样的字符串无论出现在多少个事件字段、多少次模型请求里，都是同一个
单元，一次取舍对所有出现处生效。这是必须的而不是优化：每次 `model/call` 携带当时的完整上下文，
同一条消息会随后续的每次请求再出现一次，逐处处理一定会漏。

- 流式输出按「流」拼接后算一个单元。一条流是同一分支、同一次模型请求（从 `step/model-start`
  到它的 `step/model-output-end`）里同一种类（`step/thinking` 或 `step/text`）的全部分片，
  中间夹着别的事件也不断开。分片可以短到一个字符，任意两片之间都可能切断一个标识；读包的人
  会把它们拼起来读，所以替换、取舍和校验都只看拼接后的整条流，不看单个分片，也不看相邻的
  几片。流分片事件的 `turn_id` 与 `request_id` 是结构，规格没有列到的其余字段直接丢弃，
  不生成单元，也不能通过决定文件点名追加。一条流跨了多个内容块时，它拼接后的全文与各个块
  不是同一个字符串，因此是不同的单元；点名时点的是内容块的那一个。
- 工具参数、结构化结果和 before trace 等明确列为内容的对象，键也可能是内容，所以整个对象
  序列化后作为一个单元，不拆开。
- 工具名按来源处理。来源是 `builtin` 或 `extension` 的名字保留；`extension` 的名字同时列在审阅
  文件里，提交人可以改成编号。其余来源（例如 MCP）和来源不明的名字换成编号（`tool-1`、
  `tool-2`），同一个名字在各处是同一个编号。

每个单元有一个编号（`u1`、`u2`……，按首次出现的顺序）和一个种类。同一个单元出现在几处时，种类按
下表的先后取：它的各处出现里，排得最靠前的那个种类就是它的种类。

种类不能取自首次出现的位置。导出按分支 ID 排序，所有子分支都排在 `main` 之前，而子分支的第一次
请求带着从父分支继承的全部上下文；按首次出现定种类，整段对话就都成了「其他」。按先后取则与
行的顺序无关；而且一个字符串只要在某一处被保留，它就已经在包里了，所以第 1 级的种类总是优先。

| 种类 | 来自 |
|---|---|
| 用户输入 | 用户提交的消息正文，不含后来追加的运行时文本块 |
| 助手回复 | 模型输出里的正文 |
| 思考 | 模型输出里的思考 |
| 工具参数、工具结果 | 工具调用及其结果，含后台任务的描述与输出 |
| 注入内容 | 运行时注入的规则、状态、目标、通知及其在提示词条目里的原文，以及提交检查追加的上下文 |
| 系统提示、工具定义 | 请求里的 `system` 与 `tools` |
| 附件 | 图片等二进制内容 |
| 错误信息 | 回合与模型输出结束、打断、审批取消与协作收尾时的 `reason` 与 `error` |
| 其他 | 明确列为内容的诊断对象、before trace；只在模型请求里出现、对不上任何事件字段的文本 |

在 `input/message` 的 `user.content` 里，首块即使以运行时标签开头，也不算注入内容；后续块只有文本类型且以 Dim 识别的完整运行时标签名开头，才算注入内容（见 [`markup::runtime_context`](../../crates/dim-agent-types/src/markup.rs)）。因此，提交检查追加的上下文和后续模型请求中相同的副本默认都用同一个占位；提交人有权分享时，可在第 2 级逐个点名保留。恰好与真正的用户输入或助手回复完全相同的文本，仍按上表的优先顺序归类。

审阅文件里为单元标的位置，是定下它种类的那一处。

## 分级

| 级别 | 带什么 | 谁审 |
|---|---|---|
| 0 | [`/report`](../design/plugins/Report.md#6-preview-and-sharing) 的报告 ZIP，不经过本工具。报告默认只含诊断信息。只有发送人勾选附带对话，当前会话报告才会加入近期用户和助手的片段；脱敏开关不决定是否附带对话 | 发送人在本机检查附件。公开渠道的自动摘要不含对话原文 |
| 1 | 全部事件的结构，加「用户输入」与「助手回复」两种单元 | 提交人，一次读完 |
| 2 | 第 1 级之上，决定文件点名的单元 | 提交人，逐个放行 |

第 1 级是默认。首次提交只交第 1 级；工具按提交人点名的单元决定级别，并不判断是否为首次提交。第 1 级足以回答分诊的问题：用户要什么、助手说了
什么、调了哪些工具、顺序和耗时、每段内容多大、用户在哪一步提出异议、每次操作有没有被批准、
在哪一步被打断、压缩发生在哪一轮。它不足以构建题目。

第 2 级由构建人发起。他在跟踪 issue 里写单元编号；编号就在包里的占位上，不含内容，可以公开。
提交人把它们加进决定文件，重跑，重新审阅整个待提交包后再确认。编号不变不代表内容不变：替换词、源导出或选择规则变化时，旧单元的输出也可能变化。
提交人也可以不放行；构不出题的案例按[分诊](usercases-pipeline.md#分诊)留在 issue。

决定文件还能反过来用：把第 1 级默认带上的某个单元改成省略。

**省略的单元留下占位，不改变结构。** 占位是一个固定格式的字符串，带单元编号、种类和字节数：
`[omitted u412 tool-result 1823B]`。所在字段的 JSON 类型不变：字符串换成占位字符串，整体省略的
对象换成只含一个占位成员的对象；省略的分片把占位放在第一片，其余为空串。行数、序号和每个
事件的种类都与导出一致，读导出的工具照样能读。

没有「按失败点裁剪」这一步。结构本身不含内容，而保留下来的任何一次模型请求都带着此前的全部
上下文，按序号裁剪并不缩小被带走的内容；真正决定带走什么的是单元的取舍。

## 替换

替换作用于输出里的全部字符串：保留的单元，以及结构字段里的 ID。替换表在本机，从不进入包。

| 来源 | 内容 | 自动 |
|---|---|---|
| 导出自己记录的事实 | Dim 注入的环境状态里的主目录、由它得到的用户名；Session ID；供应商侧的条目 ID 与调用 ID | 是 |
| 高置信的密钥形态 | 已知前缀的令牌、私钥块、JWT | 是 |
| 候选词 | 保留的单元里出现的：不在公开名单里的域名、主目录下的目录名、代码托管链接里的账号名 | 否，列在审阅文件里由提交人勾选 |
| 提交人自己写的词 | 人名、公司名、项目代号 | 否，写在决定文件里 |

- 主目录只从 Dim 注入的环境状态里取：工具结果里可能引用同样的标签（例如读到一个拼出这个标签
  的测试文件），把它当成主目录会让真实的用户名漏过去。环境状态里出现几个主目录就替换几个；
  一个也没有时，审阅文件提示提交人把自己的用户名写进决定文件。
- 同一个原文在整个包里换成同一个占位，调用与结果、请求与事件之间的对应关系因此保持。主会话和每个协作成员会话各用一个包内代号。请求、投递、结果和保留的对话正文引用同一会话时都用这个代号；不同会话不共用代号。
- 主目录与用户名的占位和原文等长；其余占位是短标签（`call-3`、`tool-2`、`[secret-1]`、
  `[term-1]`）。
- 拉丁字母的词按词边界匹配，其余按子串匹配；匹配不区分大小写，并覆盖 JSON 转义与 URL 编码
  两种写法。Windows 主目录同时匹配反斜杠和正斜杠写法。路径前缀之外，用户名还会单独出现
  （例如文件列表的属主列），所以用户名自己也入表。
- 两种用户名不作为单独的词替换：人人都有的账号名（`root`、`ubuntu` 等），它不标识任何人；
  短于 4 个字符的用户名，替换它会改写对话里无关的词，它改列为候选词。同理，短于 8 个字符的
  供应商 ID 只在自己的字段里换成占位，不在内容里搜索。
- 正则命中的「密钥赋值」形态（`token = …`）不自动替换。在代码会话里它几乎全是标识符，只在
  审阅文件里标成提示。
- 保留的流在拼接后的全文上替换，再按原来的边界切回各个分片；边界落在被替换的词中间时移到
  词尾，所以没有一个分片带着被替换词的一部分。

## 审阅与确认

每次运行写出两样东西：包，和只留在本机的审阅文件。审阅文件按这个顺序排：

1. 保留的单元，替换之后的全文，每个带编号、种类、位置、出现次数和扫描提示。
2. 替换表、候选词，以及保留了原名的 `extension` 工具。
3. 省略的单元，每个一行：编号、种类、位置、字节数、出现次数。
4. 被引用但不在导出里的文件，例如粘贴的文本和后台命令的输出文件。它们不会被带上。
5. 完整待提交清单，以及可以确认时使用的摘要。

未确认的包只供本机审阅，`pack/pack.json` 不含正式授权记录。在决定文件（默认是输出目录里的
`decisions.json`）里填写 `consent`，不带 `--confirm` 重跑，审阅完整的 `pack/timeline.jsonl`
和审阅文件第 5 节中的完整待提交清单。单元列表是阅读辅助，不替代检查两份文件。两份都确认后，
用第 5 节的摘要运行 `--confirm DIGEST`。授权示例：

```json
{
  "consent": {
    "diagnosis": true,
    "regression": false,
    "providers": [],
    "expires": "2027-05-16"
  }
}
```

这个例子只授权诊断。`diagnosis` 和 `regression` 必须明确填 `true` 或 `false`；`providers`
只填允许使用的供应商名称，不填凭据，未授权任何供应商就填 `[]`。允许纳入回归集时至少要列一个
供应商。`expires` 是 `YYYY-MM-DD` 格式的到期日期，到期当天仍有效。确认时按提交人本机日期
判断：授权已过期、填写不合规则或摘要对不上，都不留下包。隔天确认时 `given` 会变；需重新预览。

同一个输出目录一次只允许一个打包进程。重跑时，工具用本地凭条 `.pack-receipt` 核对上次写出的两份包文件和 `review.md`。如果有同名文件但没有有效凭条、内容被改过、目录里混入其他文件，或有符号链接或遗留的 `pack.tmp/`，工具不开始重建，也不改动这些文件。请换一个新输出目录；原目录中的文件不是本次打包结果。不要发送凭条、审阅文件或中间目录。如果进程被强制终止而留下 `.pack.lock`，先确认进程已退出，再换新目录重跑。

确认时工具把这四项和当天的 `given` 日期写入 `pack.json`，不写提交人身份。摘要与规则版本是
[授权记录](usercases-pipeline.md#授权)的「脱敏版本」。接收方核对摘要与授权，并在收件时重新
检查授权是否过期；确认时还有效，不代表收件时仍有效。私有接收仍须满足
[前置条件](usercases-pipeline.md#接收用户提交的前置条件)。

包里有两个文件：

| 文件 | 内容 |
|---|---|
| `timeline.jsonl` | 导出 v1 的行格式。头部的 `sensitive` 仍是 `true`：打包之后它依然是敏感材料 |
| `pack.json` | 证据包编号、规则版本、来源导出的版本、用到的全部模型、各种类保留与省略的单元数和字节数、占位清单（不含原文）、未包含的外部文件数、摘要；确认后另有 `consent`：三项授权范围、给出日期与到期日期 |

决定文件、替换表、单元编号与原文的对应关系留在提交人本机，与原始导出放在一起。没有它们就
回应不了第 2 级的请求，所以它们的保留期限跟随原始导出。

## 校验

通过输出目录的归属检查后，工具先清掉已核实的旧包，再生成新包。写完后重新读一遍输出：任一项不成立就不留下可交付的包，只报告哪一项、在哪个序号。

| 检查 | 不成立说明什么 |
|---|---|
| 输入以 `end` 结尾，计数相符 | 导出不完整 |
| 内容位置上的每个值是占位，或一个保留单元替换后的文本；ID 与工具名的位置上是占位或保留的名字。流式输出按整条流拼接后判断 | 取舍有漏 |
| 替换表里每个原文及其转义、编码写法在输出的任何字符串和键里都找不到，在每条流拼接后的全文里也找不到 | 替换有漏，或提交人列的词撞上了结构字段的值 |
| 输出里没有高置信的密钥形态 | 密钥出现在内容之外的位置；内容里的已经被替换 |
| 输出里没有不可读字段 | 删除有漏 |
| 行数、序号、事件种类、各字段的 JSON 类型与输入一致；不同的 ID 没有共用一个占位 | 输出不再是可读的导出 |

这一遍重新解析并重新分类输出，逐行对照输入，不复用写输出时算出的结果。

## 不靠这一步保证的事

- **自由文本里的敏感内容找不全。** 人名、业务信息、专有代码没有形态可循。本设计的回答是让
  它们默认不进输出，而不是去识别它们。
- **提交人会漏。** 所以包仍按敏感材料对待：私有存储、访问有审计、可撤回；公开的 issue 里不出现
  它的内容；进入语料的 fixture 由构建人重写，不照搬包里的原文。这几条由流水线规定。
- **省略可能把触发条件一起去掉。** 占位保留了字节数，长度相关的触发条件可以用等长的合成材料
  重建；重建得对不对，由[区分度证明](usercases-pipeline.md#构建)回答。
- **提交人无权替第三方授权。** 工具返回的内容默认全部省略，其中可能有第三方的数据；第 2 级
  放行某个工具结果之前，提交人要自己判断它是不是自己有权分享的。

## Verification

flow test 的输入是测试自己生成的合成导出，不含真实会话，不调用模型：

- 在这些位置各放一个标记串：工具结果、跨两个分片的思考、不可读字段、清单不认识的事件种类、
  非内置工具的名字与参数、只在模型请求里出现的消息、流分片里规格没有列到的字段、
  属主列形态的用户名，以及标记串的 JSON 转义与 URL 编码写法。第 1 级的输出里一个都找不到。
- 用户输入与助手回复里的标识被换成占位，同一个原文在各处是同一个占位。
- 多块用户输入中的首块运行时标签和后续普通文本都保留。提交检查追加的块及两次模型请求里的相同副本在第 1 级都省略；人为把这些副本放回时校验逐处报告，点名保留后各处均带上脱敏文本。
- 子分支排在 `main` 之前、第一次请求带着继承的上下文时，第 1 级仍带上 `main` 的用户输入与
  助手回复，审阅文件把它们标成这两个种类、位置指向 `main` 的事件；子分支排在后面时，各种类
  保留与省略的数量不变。子分支里一个引用了主目录标签的工具结果不会被当成主目录。
- 决定文件点名一个单元后，它在每个出现处都被带上并完成替换；保留的分片拼接后等于合并内容。
- 用户名被切在两个分片之间，两片之间紧挨着或夹着别的事件，每一片里都找不到用户名的任何一半；
  把原来的两半放回已写出的包，校验报告这条流。
- 同样的输入运行两次，输出逐字节相同。
- 合成 flow test 的边界导出覆盖审批、打断、压缩和协作事件：第 1 级保留审批的决定、打断的范围、
  压缩的触发与结果状态、协作的收信人；审批的调用与理由、打断的理由、权限策略、压缩的替代内容、
  协作的提示词与结果文本按内容省略。单独的图片用例也覆盖图片块的首个操作块规则；这些用例不替代
  真实导出的检查。
- 名册按 `events.rs` 的域与名字枚举核对，缺任何一个核心事件种类，测试失败。
- 确认后清单带当天的授权日期，不带提交人身份；未确认时不带授权，即使决定文件里已经填写过。
- 同一份授权在到期当天可以确认，次日拒绝确认，且不留下包。
- 能由输入触发的拒绝各有一个输入：不完整的导出、不存在的单元编号、撞上结构字段的替换词、
  内容之外的密钥、对不上的确认摘要、缺失或无效的授权。拒绝之后没有包留下。
- 防的是工具自身出错的检查，用改动已写出的包来验证：放回一段内容、一个不可读字段、一个
  供应商 ID，改掉一个序号，删掉一行，各自被报告。
- 输出的行数、序号、事件种类与字段类型和输入一致。

已知的不确定：

- 合成导出覆盖了多分支、before trace、压缩事件、带图片块的用户输入，以及协作请求与结果。
  其中协作事件的测试只检查字段的取舍，不能证明完整子 agent 会话里的委派提示会被归为哪类输入。
- 对照过的真实材料只有两份：一份单分支会话保留了内容引用；另一份是已跑通的多分支内联
  `dimcode export`。仍需用真实导出验证 before trace、压缩、图片和完整的子 agent 会话，尤其要核实
  父 agent 的委派提示是否会在子分支被记为用户输入，因而进入第 1 级。
- 「第 1 级足以分诊」是判断，没有用真实案例验证过。第一批 dogfood 案例用来验证它：报告人在
  本机打出第 1 级的包，看只凭它能否写出分诊结论。这不需要把包交给任何人。

运行结果写在 issue 或 PR 里。

## 向所有者提出的需求

无。工具读的是现有导出，写的是同一行格式；事件新增字段时默认按内容省略，不需要事件的所有者
配合。

首版是本仓库里的一个本地脚本（[pack.py](../../benchmarks/usercases/pack.py)），供内部交接案例
使用。开放外部用户提交时它需要随产品分发，那是一个新的 CLI 命令，届时另行设计并向 CLI 命令的
所有者提出；本文的规则是它的合同。

## 开放问题

- **思考默认省略的代价。** 「模型为什么这样做」常常只在思考里。它不进第 1 级是因为体积大、
  没人读得完；是否值得为它设一个更窄的默认（例如只带异议之前的最后一次请求），等第一批案例
  用下来再定。
