## 1. 范围与非目标

范围：两件与具体能力无关的事。

1. 两个存储开关，让读取不必解析正文就能筛掉与上下文无关的行；
2. 一次读取的边界：状态从哪重放，消息从哪开始收集。

非目标（都归各自的文档或实现）：

- 渲染逻辑本身：事件怎么变成消息，由 `HistoryRenderer` 决定；核心与插件事件一视同仁，扩展事件由自带渲染器处理。
- checkpoint 的内容与计算：状态怎么 set/revoke/prune，由渲染器的 checkpoint 回调决定。
- 压缩策略、状态机、超时与退避（[压缩需求](compaction-quality.md)、[ContextCompaction](plugins/ContextCompaction.md)）。
- 界面、协议、提示词内容。

## 2. 现状与问题

- 每次准备从序号 1 读取整条分支；压缩过的会话也读裁剪点之前。
- 事件表只有 `kind` 的部分索引，没有“这行是否参与渲染/状态”的入口；读取只能靠解码正文判断。

## 3. 两个开关

`timeline_events` 加两列，都是**冗余标记**，不携带内容：

| 列 | 类型 | 含义 | 谁写 |
| --- | --- | --- | --- |
| `context_render` | 0/1 | 这行参与渲染 | 写事件的一方按渲染逻辑给出 |
| `context_state` | 0/1 | 这行参与 checkpoint 状态计算 | 同上 |

规则：

1. **冗余而非真相**：真相仍是渲染/checkpoint 逻辑对事件的处理；开关只是为了不解析正文就能筛行。
2. **一行可以同时是 1/1**：渲染与状态是两种职责，互不依赖。
3. **写入时给出**：生产者知道自己写的事件是否参与渲染/状态；迁移任务按现有逻辑补。
4. **一致性由测试保证**：渲染器/折叠实际消费的行集合，必须与标记集合完全一致；不一致即失败。

## 4. 读取边界

1. **找裁剪点**：最近一次有效压缩；没有压缩时是段的起点。
2. **状态重放**：从快照的恢复位置（没有快照时从段首）开始，读 `context_state=1` 的行，把状态折叠到裁剪点及之后。
3. **消息收集**：只从裁剪点之后取 `context_render=1` 的行，交给渲染器；裁剪点自己的摘要与基线排在最前。
4. **并集读取**：消息与状态在同一次折叠里按序交互（例如输入被消费时同时出消息、更新基线），所以一次读取取两个开关的并集；两个开关仍各自决定这行参与哪一边。
4. **不删除、不改写**：裁剪点之前的事件仍然存在，只是不进入消息收集；更早的裁剪点的贡献自然不会被收集。
5. **游标**：按物理行的 `last_sequence` 前进，被过滤的行不会让游标卡住或漏行。

没有快照时状态从段首重放，代价是读取量，不是消息量。

## 5. 迁移与兼容

- 只加两列和两个部分索引：`WHERE context_render = 1`、`WHERE context_state = 1`。事件正文不变，冻结 fixture 不变。
- **填充**：两列是事件 key 的纯函数（`context_flags`）。升级在同一事务里加列并按 key 集合回填；事务提交前库不可用，提交后整体生效，不存在部分迁移的状态。不复制正文，不按会话暂存。
- **等价性**：开关集合就是渲染/折叠实际消费的集合，由差分测试证明——同一前缀上，过滤读取的 entries 与状态必须与不过滤的结果逐条一致。
- 旧版本守护进程按精确 SQL 结构拒绝新库。

## 6. 规则检查

本设计不新增事件、不新增上下文入口，渲染与状态仍走现有机制。

- **§4 rule 4**：满足。开关随事实提交，可从 Timeline 重建。
- **§4 rule 5**：满足。开关与事件同批提交，不新增批次。
- **§4 rule 6**：满足。模型上下文仍只来自既有渲染逻辑处理的事实；开关只减少被读取的行，不新增入口。
- **§4 rule 9**：满足。快照仍是可丢的派生数据。
- **ADR 002 D1–D5**：branch 作用域；不新增 wiring 模块、配置项或生命周期变化。
- **ADR 006 D1/D9**：机制只陈述一次；不重述渲染、压缩、提示词的合同。

## 7. 向所有者提出的需求

- **Runtime（TimelineStore / Timeline）**
  - 被挡住的规则：读取量不能覆盖裁剪点之前的整条分支。
  - 考虑过的机制：准备之间保留投影（需要失效规则）、一次性全量读取。
  - 通用能力：按开关与序号的分页读取、`last_sequence` 推进；以显式状态起点开始的批读入口。
  - 对序号、批次、中断、重载的影响：只读已发布事件；中断丢弃当前批；重载从事实重建。
  - owner 与 issue：runtime owner，[#708](https://github.com/arcships/dim/issues/708)。
- **Storage（原生存储）**
  - 被挡住的规则：读取要能跳过无关行，且迁移不能留下新旧并存的库。
  - 考虑过的机制：只改事件正文（要解析正文才能筛）、逐会话提交（失败会留下半迁移库）。
  - 通用能力：两列与两个部分索引、§5 的暂存/发布/启动闸门。
  - owner 与 issue：存储文档与实现。

## 8. 验收

| 项 | 方式 |
| --- | --- |
| 开关一致 | 渲染器/折叠实际消费的行集合与标记集合完全一致；新增事件种类未更新标记即失败 |
| 渲染一致 | 按开关筛选后的渲染与不过滤的渲染逐条一致 |
| 状态一致 | 按开关筛选后的折叠与不过滤的折叠状态一致 |
| 裁剪边界 | 裁剪点之前的消息不进入收集；裁剪点自己的贡献在最前；两次压缩不叠加旧摘要 |
| 无快照 | 从段首重放状态下仍只从裁剪点收消息，结果与有快照时一致 |
| 迁移 | 每个裁剪点前缀与祖先链都比对一致；任一处不一致整库回滚；崩溃后续跑；迁移未发布前守护进程不接纳该库 |
| 读取量 | 命中快照时只读裁剪点之后的渲染行与状态行；`context-breakdown` 对照 |
