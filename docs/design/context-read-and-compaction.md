## 1. 范围与非目标

范围：一次模型步骤从 Timeline 读到 `ModelRequest` 的读取计划——起点、消息与状态的产出方式、批次推进、定位查询、回退；以及压缩在这条路径里的定位语义、结算状态机与失败后果。

非目标：

- 压缩策略保留什么、摘要怎么写、质量如何判断（[压缩需求](compaction-quality.md)）。
- 提示词内容（[model-prompts](model-prompts.md)）。
- `ModelRequest` 序列化。
- **准备步骤之间保留投影**（[#710](https://github.com/arcships/dim/issues/710) 的方向）。它要求修改[上下文拼装与识别](context-assembly-requirements.md) §3.2“不引入需要失效规则的投影缓存、不在准备步骤之间保留派生位置”，那是该文档所有者的决定；本文不预设，也不依赖它。
- 界面、协议、任务执行。

## 2. 现状与问题

### 2.1 每次准备都从序号 1 重放

[history.rs](../../crates/dim-agent-capabilities/src/history.rs) 的流式入口以 `start = 1`、`state = None` 开始，只有读到压缩事件时才裁剪已累计的历史，读取范围覆盖整条分支。压缩过的会话因此每轮都读“裁剪点之前 + 之后”。

### 2.2 上下文靠渲染器识别事件类型算出来

进入模型上下文的消息由 [history.rs](../../crates/dim-agent-capabilities/src/history.rs) 按事件类型逐个折叠得到：助手消息在模型输出结束时拼出来，工具片段在调用开始/完成时拼出来，用户消息在输入被消费时拼出来。插件的事件（`Extension`，键是 `domain/name`）没有分支，直接被忽略。

后果：任何新事件要进上下文，都得改核心的折叠；插件的键是动态的，核心没法预先分类。读取过滤、checkpoint 状态也随之和事件类型绑死。

### 2.3 定位查询读整条分支

[storage/timeline.rs](../../crates/dim-app-server/src/storage/timeline.rs) 的 `policy_order` 每轮执行：

```sql
SELECT event_id, kind, sequence, json_extract(body, '$.record.event.data.through')
FROM timeline_events
WHERE session_id=?1 AND branch_id=?2 AND sequence<=?3 AND event_id IS NOT NULL
ORDER BY sequence
```

每轮把整条分支的行读一遍，并对每行做一次 JSON 提取。

### 2.4 checkpoint 是封闭结构

[checkpoint.rs](../../crates/dim-agent-types/src/checkpoint.rs) 的 `ProjectionCheckpointState` 固定写着提示词、基线、输入、配置、输出块、未闭合工具。新增一种要跨断点保留的状态就得改这个类型、升解释器版本，插件无法参与。

### 2.5 阈值压缩未完成时，失败发生在模型调用处且丢掉原因

自动压缩在准备路径里内联执行。[context_policy.rs](../../crates/dim-agent-capabilities/src/context_policy.rs) 结算后：完成则用压缩后的请求（恢复模式下仍超输入预算报 `recovery_overflow`）；取消则整个准备报取消；失败/跳过且不是恢复模式则用未压缩请求继续。未压缩请求随后被 `ModelProvider::run` 的校验拒绝，错误是“Model input exhausts its context window”，对照输入预算 `窗口 − 输出预留`。请求不会发给 provider，但**失败信息里没有压缩的结算结果与原因**。

### 2.6 证据

[#708](https://github.com/arcships/dim/issues/708) 的实测：最大会话 4,903 事件、436 次准备、累计重放 1,086,523 个事件、51 万 token、压缩与快照均为 0；进程 1.62 GiB 常驻，`malloc_trim` 归还 1.2 GiB。

## 3. 目标

- **一条恒定规则**：核心事件与插件事件用同一种方式进上下文、进 checkpoint，核心不再按事件类型写折叠分支。
- **读取量**：一次准备读取的行只与“恢复位置之后携带贡献的事件 + 当前批”有关；没有快照时仍是一次全量，但按批读取、只读贡献事件。这改变了[上下文拼装与识别](context-assembly-requirements.md) §3.2.3“每步仍然读取全量事件”，按 §9 提给该文档所有者。
- **峰值**：只与批大小和投影有关，不随历史长度线性增长。
- **checkpoint**：裁剪点 + 一张“键 → 值”的表；规则固定，内容归所有者。
- **失败语义**：压缩的每个触发方式在每种中断点都有确定终态与下一次行为；压缩未完成时的失败必须带上结算结果与原因，并以输入预算为界。

## 4. 设计

### 4.1 读取计划

四个位置不能混用：

| 名称 | 含义 | 关系 |
| --- | --- | --- |
| 锚点 | 写快照的那条压缩事实 | 事实序号大于它记录的 `through` |
| 恢复位置 | 重放开始的第一条事件 | 同一段内**早于**锚点；或在更早的祖先段 |
| 段边界 | 每一段（祖先或当前分支）固定到的序号 | 当前段是 through，祖先段是建分支时的切点 |
| 起点 | 实际开始读的位置 | 有快照时等于恢复位置，否则是第一段的序号 1 |

顺序：

1. **选快照**：按祖先段到当前段倒着试。每段取解释器一致、序号不超过该段边界的最新快照；校验锚点是对应压缩事实、事实的 `through` 早于快照序号、裁剪点与状态一致、恢复位置在固定祖先链内，同段时 `恢复位置 < 锚点`、祖先段时不超过该段边界。第一条通过的就用；该段最新候选坏了就试更早的段，全部失败才回退。
2. **定起点**：命中快照时以恢复位置为起点，否则从第一段的序号 1 开始。
3. **分段批读**：恢复位置所在段之前的段完全不读。每批默认 256 条，读一批投影一批，事件只活到当前批。
4. **回退**：没有有效快照、读取或解码失败、投影校验失败，一律从头按批重放一次，并记录回退原因。

### 4.2 贡献字段：一条恒定规则

每个事件可以带两个可选字段，核心事件和插件事件完全一样：

| 字段 | 内容 | 语义 |
| --- | --- | --- |
| 消息 | 这段事件对模型上下文贡献的消息片段（角色、内容、钉住标记） | 按事件序号追加 |
| 状态 | 一个键和它的完整值（JSON） | 覆盖该键此前的值 |

规则：

1. **谁写事件谁填字段**。模型输出结束时填助手消息；工具结果事件填工具消息；输入被消费时填用户消息；压缩事实填摘要与基线；提示词、配置、输入采纳、轮次、用量填各自的状态键。插件用自己的键填自己的消息和状态。
2. **读取只看字段**。核心按事件序号把消息追加起来，按序应用状态覆盖；不认识的事件类型只要没字段就整行跳过。核心不再按类型折叠。
3. **压缩不特殊**：摘要和基线就是压缩事实的消息字段，读取时排在最前，然后从裁剪点往后追加。既然只从裁剪点读，旧消息不会被读到，也就不需要“删除”指令。
4. **顺序**：消息按事件序号追加；同一事件内的片段保持字段里的顺序。
5. **边界**：合法的裁剪点保证没有未完成的模型输出与未闭合工具调用（现有边界校验），所以瞬时状态不需要跨断点。
6. **过滤**：存储为“是否带字段”派生一个标记，读取只取带标记的事件；`kind` 不再参与上下文过滤。标记只是索引，不参与语义。

迁移：这是不兼容的事件正文变化，按 §4.6 处理。旧事件没有字段，因此升级任务按会话跑一遍现有折叠，把每个事件的消息与状态写进新列，并比对“旧折叠的结果”与“新字段重放的结果”，一致才提交。运行时随后删掉旧折叠，只保留迁移任务里的那份实现。不留双路径。

### 4.3 定位查询与标签

需要按位置定位的只剩压缩本身：

| 查询 | 回答什么 | 标签与索引 |
| --- | --- | --- |
| 最近一次压缩尝试 | `regrown` 的边界（任何触发、任何结算）与它的 `through` | `kind='context/compaction-start'`，索引 `(session, branch, kind, sequence)` 倒序取一 |
| 最近一次完成压缩 | 起读的锚点与裁剪点 | 窄表 `status='completed'`，索引 `(session, branch, status, sequence)`；无窄表时用完成事实的部分索引（`WHERE kind='context/compaction' AND json_extract(body,'$.record.event.data.status')='completed'`，结算结果被摊平在事件数据里，路径不含 `outcome`），一行 |

轮次边界、输入窗口、用量不再单独查询：它们各自是状态键（`turns`、`inputs`、`usage`），由写它们的事件维护完整值，读取时从快照和后续状态覆盖里得到。位置一律用 `(段序号, 序号)` 的全序表达，条目带来源位置；`regrown` 的边界是写出该次尝试的那一段里、序号不大于该尝试 `through` 的最后一条事件。

压缩窄表 `timeline_compactions`（由存储文档定格式与版本）：

- 一行一次尝试：`{session_id, branch_id, start_sequence, fact_sequence, command, through, trigger, status, retain_from}`；
- 手动终止事实没有开始事件，这一行 `start_sequence` 为空、`command` 有值；
- 与压缩开始/事实在同一批次内维护，可从事件重建；
- 升级时按 `kind` 回填，只读压缩行；回填前或缺失时走上表的索引路径；
- 过滤后的批次推进按物理行的 `last_sequence` 前进，不按 `sequence + 1`。

不索引：消息正文、工具结果正文、模型输出文本。

### 4.4 checkpoint：裁剪点 + 一张表

checkpoint 只有两样：

1. `retain_from`：裁剪点；
2. 一张表：**键 → 值**，值是完整 JSON。

三条规则：

- 同一个键，断点处取最后一条；断点之前的旧值在压缩时丢掉；
- 键由写的人自己命名，要换格式就换键名，不引入版本字段；
- 单条坏了或读不出来就丢这条，不影响整份快照；快照本身仍是可丢的派生数据，校验不过就回退全量重放。

核心自己也只是几个键：`prompts`、`inputs`、`configuration`、`baseline`、`turns`、`usage`，由各自的事件维护完整值。插件用自己命名空间的键。核心不解析别人的值，只做搬运、取最新、丢坏条。

旧 snapshot 行（类型化的 v3 状态）直接作废，不迁移：它们是缓存，读不到就重放。

### 4.5 压缩状态机

状态：**判断 → 开始 → 结算 → 快照（可选）**。

不变量：

1. 每个“开始”最终都有一条“结算”。进程内由本步骤保证，**但结算写入失败时例外**：写入错误向上返回，开始保持未结算，直到下一次重载由恢复逻辑补 `Cancelled（capability reloading）`。
2. 结算单调：一条压缩只有一条结算；谁先提交谁赢。
3. 快照只出现在结算为“完成”之后，且锚定该事件；快照的构造与保存在结算之后等待，不改变结算。
4. 结算提交前，压缩不改变任何读取结果。

三类触发的后果：

| 触发 | 完成 | 取消 | 失败/跳过 |
| --- | --- | --- | --- |
| 手动 | 用压缩后的上下文，用户可见 | 记录原因，用户可见 | 记录原因，用户可见，可重试 |
| 阈值 | 用压缩后的请求；仍超输入预算 → 以结算为原因结束本轮准备 | 结束本轮准备 | 见下 |
| 恢复（provider 已拒绝过） | 仍超预算 → `recovery_overflow` | 结束本轮 | 硬失败 |

**阈值未完成或完成后仍超预算时**：以输入预算 `B = 窗口 − 输出预留` 为界。

- 未压缩请求估算超过 `B`：以明确错误结束本轮，错误里带这条结算的事件序号与原因；不再让通用校验去报“上下文超了”。
- 未压缩请求仍在 `B` 内：允许继续；结算事实（失败/跳过及其诊断）就是记录，不新增事件字段。
- 已有的 `regrown` 旁路保持不变。

**超时**：只包住策略调用。超时先通过取消令牌让策略停止并等待它持有的工作结束，再提交 `Cancelled` 并说明超时；策略在取消生效前返回的结果优先采用。结算写入与快照保存都在 `commit` 内、结算之后等待，取消检查在 `compact_step` 返回之后——这条顺序保持不变：**结算已提交后到达的取消不改变结算**。

**退避**：连续失败计数由 branch 内存维护，重载后清零；成功清零；手动压缩与恢复触发不受暂停限制；暂停后只有成功、手动、恢复或重载能解除。

**结算归属**：自动压缩的未结算开始由 `ContextPreparation::rebuild` 结算，手动命令的由 `AgentLoop` 的重建路径结算，按开始事件序号配对。

**其余中断点**：压缩开始之前就失败的准备不写压缩开始，只由准备自己的失败终态结束；策略 panic 视为失败并写结算；读到一半取消丢弃已读批次，下一次按事实重建。

### 4.6 存储格式决定

这是不兼容的持久化变化：事件正文增加两个可选字段、新增“是否带贡献”的派生标记、新增压缩窄表与若干索引。版本号由 [原生存储格式](appserver/native-storage-format.md) 决定，取落地当时的下一个可用版本，并给出从上一版原地升级的步骤：

- 加列（瞬间完成）与派生标记；
- 按会话跑一次性填充，把旧事件的贡献写进去，并比对旧折叠与字段重放的结果，一致才提交该会话；
- 回填压缩窄表；
- 旧 snapshot 行删除或忽略。

旧版本守护进程按既有门禁拒绝新库并保留字节。

### 4.7 消息与存储粒度

- 消息正文共享（`Arc<Message>`）保持；贡献字段里存的是同一份正文，不再复制。
- 文本行按 4 KiB 或 1 秒刷，思考按块一行，保持现状。
- 若 §6 测量显示行数成为瓶颈，另开设计处理块化。

## 5. 兼容性与回退

- 事件正文增加字段、快照结构改变、新增索引与窄表：都是格式变更，按 §4.6 迁移；没有运行时双路径。
- 冻结的事件 fixture 随格式决定一起更新，迁移前后各留一份对照。
- 回退：没有有效快照、校验失败、读取/解码失败，一律从头按批重放。**回退时读取量是全量**，§6 的“只读贡献事件”只对命中快照的路径成立。

## 6. 验收与测量

| 项 | 方式 |
| --- | --- |
| 迁移正确 | 每个会话：旧折叠的投影与迁移后字段重放的投影逐条一致；不一致的会话不提交 |
| 一条规则 | 核心事件与插件事件产生同样的消息与状态效果；插件加一个新键不需要改核心 |
| 起读与全量一致 | 固定前缀上，恢复位置起读与全量重放的 entries 与状态逐条一致 |
| 起读的边界情况 | 连续两次压缩、最新快照缺失、最新快照损坏、裁剪点跨批、恢复位置在祖先段、重放中途取消 |
| 跨段位置 | 祖先段上的最近尝试 + 子分支新增条目：`regrown` 与 `legal_cuts` 顺序正确 |
| 回退矩阵 | 无快照、锚点不符、解释器不符、损坏、祖先段全部失败、窄表缺失各一条流程 |
| checkpoint 规则 | 同键取最新、旧值在压缩后丢弃、坏条目只丢自己、换键名即换格式 |
| 压缩失败矩阵 | 阈值失败且超 `B` → 带结算的错误；阈值失败且 `B` 内 → 继续；阈值完成仍超 `B` → 带结算的错误；恢复失败/跳过 → 硬失败；取消 → 取消；结算写入失败 → 下次重载补结算；超时与返回竞争 → 单次结算；策略 panic → 失败结算；取消在结算之后 → 结算保留；崩溃在开始后、结算后、快照前 → 恢复逻辑与回退 |
| 退避 | 连续失败达上限后自动压缩暂停；成功、手动、恢复、重载各自解除；恢复触发不被暂停挡住 |
| 手动命令 | 开始前失败（无开始）、已有命令进行中、重载时已有命令未结算，各一条流程 |
| 读取量 | 命中快照的会话：读行数只与恢复位置之后有关；`context-breakdown` 对照 |
| 定位查询 | 用查询计划或访问行数证明两个查询不读正文行，不随前缀长度线性增长 |
| 峰值 | 与批大小相关，不随历史增长；`restore-replay` 与 `context-replay` |

不设 CI 字节阈值；数值写进实现 PR。

## 7. 风险与备选

| 项 | 说明 |
| --- | --- |
| 迁移写错 | 每个会话提交前比对旧投影；不一致即中止该会话 |
| 字段漏填 | 生产者漏填会让上下文缺内容；迁移比对与流程测试覆盖，核心不再有类型折叠可依赖 |
| 快照语义漂移 | §4.1 的校验拒绝不匹配的快照；拒绝即回退 |
| 键冲突 | 键由所有者命名；核心键固定前缀，插件用自己的命名空间 |
| 备选：准备之间保留投影 | 需要改[上下文拼装与识别](context-assembly-requirements.md) §3.2，由该所有者决定；不在本文 |

## 8. 规则检查

本文涉及的部分都是 Capability：[history.rs](../../crates/dim-agent-capabilities/src/history.rs)、[context_policy.rs](../../crates/dim-agent-capabilities/src/context_policy.rs)、[context_preparation.rs](../../crates/dim-agent-capabilities/src/context_preparation.rs)、[agent_loop.rs](../../crates/dim-agent-capabilities/src/agent_loop.rs)。

- **§4 rule 1**：不适用。读取只读已提交事实；快照与窄表是派生状态。
- **§4 rule 2**：不适用，交接没有变化；读取按已提交序号处理，失败丢弃当前批。
- **§4 rule 3**：不适用，没有 before 回调。
- **§4 rule 4**：满足。Timeline、Dispatcher、批次不变；消息与状态是事实自带的字段，可从 Timeline 重建；退避计数是内存态。
- **§4 rule 5**：满足。不新增批次；字段随事件同批提交。
- **§4 rule 6**：满足。消息仍只来自已提交事实；差分测试在固定前缀上比对。
- **§4 rule 7**：满足。读取使用 Timeline 的公开入口；窄表与索引是存储内部实现。
- **§4 rule 8**：**不满足**，需要机制所有者新增能力，见 §9。
- **§4 rule 9**：满足。快照仍是可选派生状态，不能替代事实；状态值本身写在事件里。
- **ADR 002 D1–D5**：branch 作用域；不新增 wiring 模块、配置项或生命周期变化；接口语言中立；§9 明确列出需要新增的公开入口。
- **ADR 006 D1/D9**：规则只在本层陈述一次；本文不重述存储、压缩质量或提示词合同。

## 9. 向机制所有者提出的需求

- **Runtime（TimelineStore / Timeline）**
  - 被挡住的规则：模型上下文必须能从已提交事实重建，同时一次准备的读取量与峰值不能是恢复位置之前的全量。
  - 考虑过的机制：准备之间保留投影（需要失效规则，且要求改[上下文拼装与识别](context-assembly-requirements.md) §3.2）、持久投影快照（已有，跨装载）、一次性全量读取（峰值 45 MB）。
  - 通用能力：按“是否带贡献”与序号的分页读取与 `last_sequence` 游标推进；按 `kind` 与标签的定点选择；以显式初始状态与起点开始的批读入口。
  - 分工：运行时只提供通用索引选择，压缩的完成语义由 Capability 判断。
  - 对序号、批次、中断、重载的影响：只读已发布事件；不新增批次；中断丢弃当前批；重载仍从事实重建。
  - owner 与 issue：runtime owner，[#708](https://github.com/arcships/dim/issues/708)。
- **Storage（原生存储）**
  - 需求：两个贡献字段、“是否带贡献”的标记与索引、压缩窄表与回填、§4.6 的迁移任务；格式版本由该文档决定。
  - owner 与 issue：存储文档与实现。
- **上下文拼装与识别（requirements owner）**
  - 需求：§3.2.3“每步仍然读取全量事件”改为“读取量只与恢复位置之后有关”；§3.2.4/§3.2.5 的缓存与派生位置结论不变。
  - owner 与 issue：该文档所有者，[#708](https://github.com/arcships/dim/issues/708)。
- **HistoryRenderer / ContextPolicy / ContextPreparation / AgentLoop（本 capability）**
  - 需求：§4.1 的读取计划、§4.2 的字段规则、§4.4 的 checkpoint 规则、§4.5 的结算语义；由本文自身的实现承担。
