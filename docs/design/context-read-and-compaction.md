## 1. 范围与非目标

范围：一次模型步骤从 Timeline 读到 `ModelRequest` 的完整读取路径——起点怎么选、读哪些行、如何投影、策略需要哪些事实、失败怎么回退；以及压缩在这条路径里的定位语义和它与失败/中断的因果关系。

非目标：

- 压缩策略保留什么、摘要怎么写、质量如何判断（[压缩需求](compaction-quality.md)）。
- 提示词内容与指引（[model-prompts](model-prompts.md)）。
- 事件种类、事件正文格式、`ModelRequest` 序列化。
- 界面、协议、任务执行。

## 2. 现状与问题

### 2.1 每次准备都从序号 1 重放

[history.rs](../../crates/dim-agent-capabilities/src/history.rs) 的流式入口以 `start = 1`、`state = None` 开始，压缩只在读到压缩事件时裁剪已累计的历史；读的量与投影的量仍然覆盖整条分支。压缩过的会话因此每轮都读“裁剪点之前 + 之后”，峰值也包含裁剪点之前那批投影。

[上下文重建的内存计划](context-replay-memory.md) 的 P3 把峰值降到了跟批大小相关，但明确把 CPU/IO 排除在外，所以这条读取路径没有新增起点语义。

### 2.2 定位查询读整条分支

[storage/timeline.rs](../../crates/dim-app-server/src/storage/timeline.rs) 的 `policy_order` 每轮执行：

```sql
SELECT event_id, kind, sequence, json_extract(body, '$.record.event.data.through')
FROM timeline_events
WHERE session_id=?1 AND branch_id=?2 AND sequence<=?3 AND event_id IS NOT NULL
ORDER BY sequence
```

也就是每轮把整条分支的行读一遍，并对每行做一次 JSON 提取，只为得到轮次起点、压缩起点和“某个裁剪点 id 是否在分支内”。正文里的定位信息没有列或索引。

### 2.3 两个读取入口

运行时已经有从快照恢复位置起读的入口（[timeline.rs](../../crates/dim-agent-runtime/src/core/timeline.rs) `context_with_checkpoint`），完整路径在用；流式入口绕开它。同一个问题因此有两套语义：一套能起读但物化整段历史，另一套不物化但不起读。

### 2.4 压缩失败没有确定的后果

自动压缩在准备路径里内联执行（[context_policy.rs](../../crates/dim-agent-capabilities/src/context_policy.rs)）。结算后的分支是：

- 完成：用压缩后的请求；恢复模式下再检查是否仍超预算，超了报 `recovery_overflow`；
- 取消：整个准备报取消；
- 失败/跳过且不是恢复模式：`Ok((view.prepared, estimate.input))`，直接发送未压缩的请求。

也就是说阈值触发是“尽力而为”：失败或跳过后不重试、不退避、不检查未压缩请求是否已超过上下文窗口，直接发给 provider。超过窗口时只能由 provider 报错。

### 2.5 证据

[#708](https://github.com/arcships/dim/issues/708) 的实测：最大会话 4,903 事件、436 次准备、累计重放 1,086,523 个事件、51 万 token、`context/compaction` 与 `timeline_snapshots` 均为 0；进程 1.62 GiB 常驻，`malloc_trim` 归还 1.2 GiB。

## 3. 目标

- **读取量**：一次准备读取的行数只与“断点之后的未被过滤事件 + 当前批”有关，不随断点之前的长度增长；断点不存在时（从未压缩）仍是一次全量，但同样按批读取、按类型过滤。
- **峰值**：只与批大小和投影有关，不随历史长度线性增长。
- **一致性**：任何起读路径的结果必须与全量重放逐条一致；不一致即回退，不猜。
- **定位**：策略和读取计划需要的定位信息来自列或窄表，不来自正文的逐行提取。
- **失败语义**：压缩的每个触发方式在每种中断点都有确定的终态和下一次行为；不允许“压缩没完成但请求照发且没人知道”。

## 4. 设计

### 4.1 读取计划

一次准备的读取按以下顺序决定：

1. **找断点**：查询这条分支上最近一条 `Completed` 压缩（只取保留点、through 与状态，见 §4.3）。没有断点则走全量批读。
2. **取跨断点状态**：在断点处取最新且校验通过的可选快照（解释器一致、锚点为该压缩事件、`retain_from` 一致、恢复位置在固定祖先链内，见 §4.4）。校验通过则以快照状态为初始投影状态、以压缩事件为起点；没有快照或校验失败则回退全量重放（§4.5 的“从事实推导状态”是后续项）。
3. **批读与投影**：从起点按序号批读，按 §4.2 只取投影需要的事件种类；每批投影后立即释放原始事件。压缩事件本身在批次内照常重放，由它安装替代内容（摘要与基线）。
4. **策略查询**：配置、用量、预算、轮次边界、当前输入与窗口各用 §4.3 的窄查询，不再由读取路径顺带产出。
5. **同装载续读**（对应 [#710](https://github.com/arcships/dim/issues/710)）：branch 内保留上一次准备的最终投影与续读位置，下一次只读新增事件。边界失效时丢弃并回到第 1 步：压缩完成、提示词或配置 revision 变化、分支切换、输入被撤回、投影校验失败、装载重载。保留的只是可重建的派生状态，不是事实。

读取计划的输入输出是一份显式结构（起点、初始状态、批次大小、过滤集合、回退原因），而不是“流式或全量”两个布尔分支。

### 4.2 事件分类与过滤

过滤的前提是声明每种事件对投影的作用。分类只有三类：

| 类别 | 含义 | 例子 |
| --- | --- | --- |
| 投影 | 改变模型可见消息或跨断点状态 | `input/*`、`step/text`、`step/thinking`、`step/tool-use`、`tool/result`、`context/configured`、`context/compaction`、`prompt/*` |
| 定位 | 不改变消息，但策略需要位置与预算 | `turn/start`、`turn/end`、`context/compaction-start`、`context/prepare`、`context/budget`、`model/usage` |
| 进度 | 只服务界面、树视图、验收与审计 | `step/model-start`、`step/tool-use-start`、`step/model-output-end`、`model/call`、`approval/*`、`branch/*` |

规则：

- 分类表是编译期常量，外加一个穷举测试：`EventKind` 新增变体而未归类即失败。
- 读取只解码“投影”与“定位”两类；定位类可以由窄查询直接产出，不进入批次。
- “进度”类不进入读取路径，只由各自的消费者读取。
- 分类错误的结果是上下文不同，所以除了穷举测试，还要有 §6 的差分测试兜底。

### 4.3 定位标签与索引

`timeline_events` 已有列：`session_id`、`branch_id`、`sequence`、`last_sequence`、`kind`、`body`、`event_id`；主键 `(session_id, branch_id, sequence)`，另有 `event_id` 的部分索引与一条工具调用的部分索引。缺的是可以按类别和标签定位的入口。

新增（由存储格式决定，见 §4.6）：

- `kind` 的通用索引：`(session_id, branch_id, kind, sequence)`；
- 压缩窄表：每次压缩一行，`{session_id, branch_id, start_sequence, fact_sequence, through, retain_from, status}`，由事实事件派生，可从事件重建；
- 轮次与用量的标签：`turn_id`（轮次开始/结束、预算）、输入 id（采纳与消费）、工具 `call_id`（调用与结果）——按查询需要加成列或索引；
- 明确不索引的内容：消息正文、工具结果正文、模型输出文本。

策略需要的三个查询因此变成定点查询：最近压缩、断点之后的轮次边界、窗口内的事件与工具结果。`policy_order` 的整分支扫描退役。

### 4.4 快照与压缩事实

因果关系不变，写清楚在这里：

- 压缩事实是真相：`retain_from`、替代内容、基线、诊断都在事件里，可以完整重建上下文。
- 快照是可选缓存：在事实提交之后写入，锚定该压缩事件，内容是断点之前的跨断点状态与恢复位置；写入失败只告警。
- 快照只在四条校验都成立时被采用；任何一条不成立即丢弃并回退全量。

起读只依赖这两者，不引入第三份状态。

### 4.5 压缩状态机与失败语义

状态：**判断 → 开始 → 结算 → 快照（可选）**。

不变量：

1. 每个“开始”最终都有一条“结算”。进程内由本步骤保证；崩溃或重载由下一代的恢复逻辑补 `Cancelled（capability reloading）`。
2. 结算单调：一条压缩只有一条结算事件。
3. 快照只出现在结算为“完成”之后，且锚定该事件。
4. 结算事件提交前，压缩不改变任何读取结果。

三类触发的后果要求：

| 触发 | 完成 | 取消 | 失败/跳过 |
| --- | --- | --- | --- |
| 手动 | 用压缩后的上下文 | 记录原因，用户可见 | 记录原因，用户可见，可重试 |
| 阈值 | 用压缩后的请求 | 结束本轮准备 | 见下 |
| 恢复（provider 已拒绝过） | 仍超预算 → `recovery_overflow` | 结束本轮 | 硬失败 |

**阈值触发未完成时**（本次修正的语义）：

- 未压缩请求的估算输入 **超过上下文窗口**：以明确错误结束本轮准备，不发送。错误里带结算结果与原因。
- 未压缩请求仍在窗口内：允许继续发送，但在 `context/prepare` 或预算事件里记录“本步压缩未完成及原因”，下一次准备仍会重新判断。

**退避与超时**：连续失败达到阈值后暂停自动压缩并提示用户（手动仍可用），成功后清零；单次策略调用有上限，超时按取消结算，超时也计入失败次数。具体阈值由实现给出常量，本文只要求存在且可观测。

**观测**：完成/跳过/失败/取消的原因、耗时、估算输入与结算后输入都已在压缩与预算事件里；窄表与查询让它们可被检索。

### 4.6 存储格式决定

新增索引与压缩窄表是存储格式变更。本设计不写版本号：由 [原生存储格式](appserver/native-storage-format.md) 的规则决定，取落地当时的下一个可用版本，并给出从上一版原地升级的步骤。窄表与标签列都可以从事件重建，升级不需要回填业务数据；旧版本守护进程按既有门禁拒绝新库并保留字节。

### 4.7 消息与存储粒度

- 消息正文共享（`Arc<Message>`）已经落地，保持。
- 文本行按 4 KiB 或 1 秒刷（[output.rs](../../crates/dim-agent-capabilities/src/output.rs)），思考按块一行，保留现状：合并行会改变崩溃丢失上界与界面续播粒度，而当前行数的大头是每步的协议事实，不是正文分段。
- 若按 §6 测量后发现行数仍是瓶颈，另开设计处理块化，不在本文范围。

## 5. 兼容性与回退

- 事件种类、正文、快照格式、`ModelRequest` 序列化不变；冻结的事件 fixture 不动。
- 新增索引与窄表：存储格式变更，按 §4.6 处理；窄表是派生数据，损坏可重建。
- 回退：没有快照、锚点不符、解释器不符、快照损坏、祖先分支、自定义渲染器、分类缺失——一律回退全量重放，并记录回退原因。
- 同装载续读在任何边界失效时立即丢弃，回到全量或断点起读；它不写任何事实。

## 6. 验收与测量

| 项 | 方式 |
| --- | --- |
| 起读与全量一致 | 固定前缀上，断点起读与全量重放的 entries 与状态逐条一致 |
| 过滤一致 | 分类过滤后的投影与不过滤的投影逐条一致；穷举测试覆盖新增事件种类 |
| 回退矩阵 | 无快照、锚点不符、解释器不符、损坏、祖先分支、自定义渲染器各一条流程 |
| 压缩失败矩阵 | 阈值失败且超窗口 → 明确错误；阈值失败且窗口内 → 继续且有记录；恢复失败/跳过 → 硬失败；取消 → 取消；崩溃在开始后、结算后、快照前 → 恢复逻辑与回退重放 |
| 读取量 | 压缩过的会话：读行数只与断点之后有关；`context-breakdown` 对照 |
| 峰值 | 与批大小相关，不随历史增长；`restore-replay` 与 `context-replay` |
| 定位查询 | 单次准备的定位查询不再读取正文行；用 SQL 计数验证 |
| 压缩可观测 | 失败次数、原因、耗时可从事件与窄表检索 |

不设 CI 字节阈值；数值写进实现 PR。

## 7. 风险与备选

| 项 | 说明 |
| --- | --- |
| 分类漏项 | 上下文会不同；穷举测试 + 差分测试兜底 |
| 快照语义漂移 | 四条校验拒绝不匹配的快照；拒绝即回退 |
| 窄表与事实重复 | 窄表只存定位字段，可从事件重建；升级不回填业务数据 |
| 同装载续读 | 只保留可重建的派生状态；边界失效即丢弃；不写事实 |
| 备选：定期投影点 | 未压缩长会话要停止重放只能这样做；需要写入频率、体积与失效规则，本文不做 |
| 备选：内存投影缓存 | 就是同装载续读；跨装载不保留 |
| 备选：提前压缩 | 改变上下文质量与成本，属于产品参数，不在本文 |
| 未做 | 跨会话共享投影、磁盘投影快照、自动调参 |

## 8. 规则检查

- **§4 rule 1**（改别的模块的状态要写指令事件）：不适用。读取只读已提交事实；窄表与快照都是派生状态，不是别的模块的业务状态。
- **§4 rule 2**（交接后不能撤回）：不适用，交接没有变化；读取只按已提交序号处理，失败丢弃当前批。
- **§4 rule 3**（before 只同步变换草稿）：不适用，没有 before 回调。
- **§4 rule 4**（核心机制不带业务含义）：满足。Timeline、Dispatcher、批次不变；投影与分类属于 capability 自己的读取语义。
- **§4 rule 5**（原子批次提交、按序派发）：满足。不新增批次、不写事件；读取按已提交序号。
- **§4 rule 6**（模型上下文只包含交接后被读取的事件）：满足。过滤不改变采纳与消费规则，只减少被解码的事件；差分测试在固定前缀上比对。
- **§4 rule 7**（插件只通过公开事件和服务交互）：满足。读取使用 Timeline 的公开入口；窄表与索引是存储内部实现，不成为跨插件接口。
- **§4 rule 8**（基础设施默认不变）：**不满足**，需要机制所有者新增能力，按五项列出（见 §9）。
- **§4 rule 9**（只有后续决定要用的事实才进 Timeline）：满足。压缩事实与快照的边界不变；快照仍是可选派生状态，不能替代事实。
- **ADR 002 D1–D5**：branch 作用域；不新增 wiring 模块、配置项或生命周期变化；读取接口保持语言中立；不要求其他模块使用尚不存在的 API（§9 明确列出需要新增的公开入口）。
- **ADR 006 D1/D9**：规则只在本层陈述一次；本文不重述存储、压缩质量或提示词的合同，只引用。

## 9. 向机制所有者提出的需求

- **Runtime（TimelineStore / Timeline）**
  - 被挡住的规则：模型上下文必须能从已提交事实重建，同时一次准备的读取量与峰值不能是断点之前的全量。
  - 考虑过的机制：内存投影缓存（引入跨步骤失效状态）、持久投影快照（已有，跨装载但仍需整段解码）、一次性全量读取（峰值 45 MB）。
  - 通用能力：按 `kind` 与标签的分页读取；最近完成压缩的窄查询；断点之后的轮次边界与窗口查询；以显式初始状态与起点开始的批读入口。
  - 对序号、批次、中断、重载的影响：只读已发布事件；不新增批次或事件；中断丢弃当前批；重载后仍从事实重建。
  - owner 与 issue：runtime owner，[#708](https://github.com/arcships/dim/issues/708) / [#710](https://github.com/arcships/dim/issues/710)。
- **Storage（原生存储）**
  - 需求：§4.3 的索引与压缩窄表的格式决定、升级与升级保护；窄表损坏可重建。
  - owner 与 issue：存储文档与实现，版本决定由该文档给出。
- **HistoryRenderer / ContextPolicy / AgentLoop（本 capability）**
  - 需求：§4.1 的读取计划、§4.2 的分类、§4.5 的失败语义与退避；由本文自身的实现承担。

## 10. 删减检查

- 不新增缓存层：同装载续读复用现有投影状态，边界失效即丢弃；跨装载只保留既有快照。
- 不新增事件、不新增配置项、不新增协议字段。
- 窄表只存定位字段，且可从事实重建，不成为第二份真相。
- 分类是常量表加穷举测试，不引入运行时注册或插件接口。
- 不改变压缩策略与摘要内容；不合并存储行；不引入内存统计接口。
