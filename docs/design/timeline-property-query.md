# Timeline 属性查询与消费端改造

Scope: Timeline 读取机制，以及状态恢复、请求构造对它的使用。
决策依据：[ADR 022](../adr/022-event-property-queries.md)。本文定义查询接口和执行约定。
相关问题：[#1147](https://github.com/arcships/dim/issues/1147)。既有 issue、PR 的范围不由本文自动扩大。

相关设计：[数组下标点读](timeline-array-rows.md)复用既有 Fields 路径；[成员索引](appserver/timeline-member-index.md)定义反关联索引；[状态结果](owner-state-indexed-reads.md)区分各owner的业务保存与运行内存。不增加 QuerySpec.rows 或通用状态 CRUD。

## 1. 修改范围

| 对象 | 需要修改的行为 |
| --- | --- |
| 查询接口 | 从返回完整事件，改为返回指定字段、计算结果或明确请求的完整事件。 |
| Timeline | 确定一次读取的范围，把整个范围交给存储；不逐分支查询后拼接。 |
| 存储 | 在逻辑事件上筛选、关联、分组，再分页；只解码参与查询的正文。 |
| 恢复逻辑 | 查询自己需要的状态依据，不收集完整历史事件。 |
| 上下文部件 | 确定本次请求需要的内容，再读取正文；请求由本次操作持有。 |

入口和模块归属见 [ADR 022 D2](../adr/022-event-property-queries.md#d2-目标-api-与模块结构)。本设计不增加独立查询服务、Capability、业务投影表或新的上下文入口，也不修改事件格式。提交标识索引采用存储所有者定义的 v35 格式升级，派生文本索引采用 v36 升级。

## 2. 查询接口

### 2.1 请求和结果

四个读取入口共用下表的数据。`query` 是异步操作；取消结束本次读取，不写入事实。普通门面的可见性限制、结束分支的本分支读取限制沿用[读取归属](timeline-read-ownership.md)。

| 请求字段 | 约定 |
| --- | --- |
| `scope` | `branch` 或 `chain`。链按祖先到当前分支排序，各祖先截止到分叉点。 |
| `from` | 可选的 `TimelinePosition`，包含该位置。不填则从范围起点开始；不能指向范围外的分支或位置。 |
| `through` | 当前分支的截止序号，包含该位置；`0` 表示当前分支没有事件，祖先仍按分叉点读取。首次省略时由入口确定，后续页必须传回。 |
| `include_publishing` | 内部部件可读取已原子提交、尚未发布的事实，用于恢复及准备重试。普通门面只读已发布事实。 |
| `query.filter` | 字段条件、逻辑组合和关联存在条件。省略表示范围内全部事件。 |
| `query.select` | 必填：字段行、完整事件、计数或是否存在。字段行明确列出返回字段，不隐含完整事件。 |
| `query.group_by` | 可选的分组字段列表。分组时选择计数，或通过 `query.pick` 选择每组的事件。 |
| `query.pick` | `first` 或 `last`，按事件顺序选一条，再读取这条事件的返回字段。无分组时作用于整个筛选结果；不能与计数、存在判断组合。 |
| `query.order_by` | 字段或事件顺序及升降序；只决定最终结果的排列，不改变 `pick` 的含义。默认事件升序；分组计数默认分组键升序。 |
| `page` | 多行结果必填：正数 `limit` 和可选 `after`。未分组的计数、存在判断不分页。 |

字段行保留所选字段的顺序。字段结果区分三种形态：`missing`、单个 JSON 值、数组路径的逐项取值；后者每项也区分 missing 与 JSON 值。显式 `null` 是 JSON 值，不代表 missing。完整事件结果逐项携带 `TimelinePosition` 和完整 `AgentEvent`；不再依赖两组数组按下标配对。分组结果额外携带分组键；数值相等但表示不同的键（如 `1` 和 `1.0`）使用组内第一条事件的表示。计数返回非负整数。无匹配时，行结果为空、计数为 `0`、存在判断为 `false`。

结果统一携带实际 `through` 和 `next`。`next` 是无服务端状态的续读数据，绑定 Session、分支、范围、查询表达式和最后一行的排序键；调用方原样传回。它不持有 Reader，也不赋予额外读取权限。

事件顺序是分支段顺序加段内序号。按字段排序时，追加事件顺序作为唯一的末尾排序键；分组计数追加完整分组键。`after` 只限制最终输出，不能缩小关联查询的范围。查询变化、范围变化、续读数据不匹配、未来截止位置均为输入错误，不自动换成新查询。

分组计数只能按分组键或计数排序，不能引用组内任意一条事件的字段。分组取值必须指定 `pick`；`exists` 不接受分组。这些组合在入口校验。

### 2.2 字段和运算

字段引用分为事件属性与位置属性。事件属性包括 `kind`（`domain/name`）、`id`、`create_at`、`tags`、`data` 下的字段和上下文标志；位置属性使用 `TimelinePosition`。`data` 中的名字沿用公开事件字段，不暴露数据库列、内容哈希或消息链节点。

| 能力 | 限定 |
| --- | --- |
| 字段取值 | 对象字段路径；数组路径允许一个 `[]`。投影 `data.calls[].id` 返回按原顺序排列的值，元素缺字段时保留 `missing`，不改变数组位置。条件、投影、分组及排序也支持固定下标，如 `data.blocks[0].text`；下标从 0 开始，非数组、越界或元素缺字段返回 `missing`。 |
| 条件 | 等于、不等于、大小比较、属于给定集合、字段存在、字符串前缀和包含；可用 `and`、`or`、`not` 组合。数组条件显式使用 `any`，同一个 `any` 中的条件作用于同一元素。 |
| 关联 | `exists` 或 `not exists`：在同一读取范围中，以内层字段与外层字段比较。内层可以再加普通字段条件和关联，不返回内层事件。`outer` 指直接外层事件，`root` 指本条结果正在判断的最外层事件；两者仅在关联中可用，不能越出固定读取范围。 |
| 字符串构造 | `concat.parts` 按顺序连接字符串操作数；任一项 missing 或不是字符串时返回 missing，不隐式转型。它用于将已有 ID 与固定标签前缀比较，不计算渲染正文。 |
| 计算 | 是否存在、计数、分组计数、每组第一条或最后一条。需要最新配置的一组字段时，它们来自同一条事件，不能分别取最大值。 |

这些是有限的数据表达式，不接收 SQL、脚本、函数或业务状态名称。数组和对象可以作为返回值；比较、分组、字段排序只接受标量，不能隐式把数组展开成多条事件。

每个字段名后最多跟一个数组选择符：`[]` 或 `[n]`。`n` 是 0 至 2147483647 的十进制整数，不带符号、空白或前导零；可在不同层级分别使用固定下标。`[]` 只用于投影，固定下标不增加返回行数。`null` 元素自身存在，但其子字段为 `missing`。

缺字段、类型不匹配的比较结果为 `false`；检查缺字段使用字段存在条件的否定。显式 `null` 只与 `null` 相等，布尔值不等同于数字，字符串不转数字。数字按数值比较，字符串按 UTF-8 字节顺序比较；分组也遵守这些等价关系。排序的类型顺序为 missing、null、boolean、number、string，同类按值排序，降序反转。动态事件中出现不能排序或分组的值时返回查询错误，不丢弃该事件。

非法表达式在服务入口解析时拒绝；范围由 Timeline 校验；存储损坏在存储边界报错。沿用现有输入错误、未知分支、关闭、存储错误和取消类别；不把失败返回为空结果。进入系统后的查询对象直接传递，不逐层重新解析。未知事件类型或合法但不存在的字段不是格式错误。SQL 和内存实现必须给出相同结果，包括 missing、null、数值和数组条件。

### 2.3 不需要完整事件的业务查询

| 需要 | 查询 |
| --- | --- |
| 查询提交是否存在 | 提交标识相等，返回存在判断；提交入口需要区分冲突时返回至多两条身份字段。 |
| 读取最近配置 | 筛选配置类型，`pick=last`，只选配置字段。 |
| 按键读取有效配置 | 筛选相关变更，按配置键分组取最后一条，保留删除或停用标志，由配置所有者解释。 |
| 恢复未结束操作 | 筛选开始事件，排除存在对应终态的事件，只选结算需要的字段。 |
| 构造请求 | 查询采用关系、压缩边界和有效内容的位置，再按这些位置读取正文。 |

“是否已有提交”的读不能代替提交锁或唯一性约束。提交入口固定已提交上界，查询至多两条匹配身份，包含尚未发布的尾部；随后取得提交锁。若上界已变化，释放锁后重新查询；否则在锁内返回已有提交或写入新输入。数据库读取不占用提交锁。入口不建立历史提交标识表，仍保留重复与冲突语义。

## 3. Timeline 如何确定读取范围

Timeline 在锁内取得可见上界、分支链和本次读取所需的内存尾部引用，然后释放锁。数据库 I/O、查询计算、正文解码均在锁外进行。

交给存储的 `read_scope` 包含 Session、按链顺序排列的分支段、每段的闭区间，以及内存尾部。每条事实恰好来自一个输入：已落盘的区间或尾部引用。尾部在查询过程中落盘，也不能再被数据库输入重复读到。后续页可以重新划分落盘区间和尾部，但读取的事实集合必须相同。

截止位置不因后续追加而前移。一次状态恢复中的所有查询复用同一个截止位置；恢复交接遵循 [ADR 020 D3](../adr/020-timeline-read-convergence.md#d3-replay-is-removed)。查询结果可以在原子批次内分页，但输入只能包含已经提交、满足可见性要求的事实。

`from` 限制整个查询范围，包括关联的两端。若历史开始事件仍可能影响当前状态，业务不能把 `from` 随意设成最近一轮。若只想分页，使用 `after`，不要改变 `from`。

TimelineTree 为结束分支使用自己持有的固定 head，不重新装载分支。结束分支的 `chain` 查询仍按现有契约拒绝。本次改造不改变 Session acquire、分支目录或数据库导出的入口。

## 4. 存储执行

### 4.1 先取得逻辑事件，再计算

SQLite 一条 `timeline_events` 记录可能包含多个输出事件。物理记录只用于定位，不能直接成为分页单位。

| 存储形态 | 事件位置和属性来源 |
| --- | --- |
| 普通记录 | `$.record.event`。 |
| 合并输出记录 | `json_each(body, '$.records')` 中每项的 `$.event`。 |
| 内存尾部 | 已有类型化事件的字段；只提取表达式所需字段，不把整个事件先序列化成 JSON。 |

合并输出的 `turn_id`、`request_id` 保存在物理行的共享头中。查询这两个属性时从共享头取值；返回 `data` 或完整事件时在存储边界恢复这两个字段，不能把记录内省略的字段判断成 missing。

执行顺序固定为：

1. 按 Session、分支段、序号交集定位物理记录。复用现有位置、类型、事件标识和标志索引；只下推不会漏掉逻辑事件的条件。
2. 把普通记录和合并记录中的事件统一为逻辑行。逐条检查上下界；合并行中起点之前的匹配不算匹配。
3. 在全部分支段和尾部组成的同一范围中执行条件、关联、分组和选择。
4. 按稳定排序键取 `limit + 1` 条最终结果，用多出的一条决定是否返回 `next`。
5. 若返回字段包含正文，解码本页实际返回行所需的内容。

第 5 步只适用于正文仅被返回的情况。正文参与筛选、关联、分组或排序时，必须先按下一节取得它，不能分页后补筛。

关联查询的内层保留完整固定范围；外层物理候选单独应用位置游标，不能为此缩小内层范围。文本候选的成员判断按 `(分支段, 逻辑位置)` 或 `(分支段, 物理位置)` 的临时索引查找，不为每条事件重建一份候选列表。

当 OR 的每个分支都有覆盖当前事件类型的文本候选位置时，先合并这些位置，再按位置索引读取事件；候选为空时不扫描事件表。任一分支没有完整候选覆盖，就不能用该位置并集限制整个 OR。候选仍需原始条件验证，合并输出、未索引类型和未覆盖尾部保持原语义。

普通字段查询直接编译为参数化 SQL；不先把全范围复制到临时表。物理行不足一页、解码后本页没有匹配，都不能作为查询结束的依据。

字段只用于存在判断时，SQL 中间结果只保留存在标记，不复制字段正文；显式 null 仍算存在。

下面展示审批未结束集合的 SQL 语义。`events` 指上面已经限定范围的逻辑行；实际 SQL 按字段需求读取索引列或 JSON 路径，不构造 `AgentEvent`。

```sql
SELECT a.branch_id, a.sequence, a.approval_id
FROM events AS a
WHERE a.kind = 'approval/request'
  AND NOT EXISTS (
    SELECT 1 FROM events AS z
    WHERE z.kind IN ('approval/respond', 'approval/cancelled')
      AND z.approval_id = a.approval_id
  )
ORDER BY a.segment_order, a.sequence
LIMIT :limit_plus_one;
```

查询的分页条件只加在外层 `a` 上。终态位于上一页、祖先分支或内存尾部，仍然可以消除这条开始事件。其他业务自行提供完整关联键，例如模型调用使用 `turn_id` 和 `request_id`，不能由存储猜测。

等值关联优先使用已有索引；没有合适索引时，一次提取内层关联键，交给本次 SQL 执行的临时索引参与关联。不能对每条开始事件重新扫描、解析整段终态历史。验收同时检查查询计划和扫描量，不能仅把业务循环改写成逐条相关子查询。

分组取最后一条可以使用 `row_number() over (partition by 分组键 order by segment_order desc, sequence desc)`，取排名为 1 的整条字段行。不得分别对各字段使用 `max`。

### 4.2 内容引用只解码所需部分

请求的 `messages`、`tools`、`system` 可能通过引用保存。压缩后的行内字段不是完整事件属性，不能用空消息数组或缺少的 `system` 直接参与查询。

| 需要的属性 | 解码工作 |
| --- | --- |
| 请求标识、模型标识、事件位置等行内字段 | 读取对应字段，不创建消息链 Reader。 |
| `request.system` 或其子字段 | 只读取 system 引用。 |
| `request.tools` 或其子字段 | 只读取 tools 引用。 |
| `request.messages` 或其子字段 | 沿 `list → parent` 读取消息链，恢复原顺序；不连带读取 tools 和 system。 |
| 完整请求或完整事件 | 读取其全部必要内容；不连带展开不属于该查询的 trace。 |

内容读取复用 codec 的哈希、类型、链长度等校验以及已有格式兼容。不能用 SQL 直接连接内容表来绕过这些校验。链节点共享只存在于本次读取中；读取结束、失败或取消后释放。

正文只作为返回字段时，先选出本页事件位置，再解码。正文参与条件或计算时，SQLite 先用行内条件缩小候选范围，再分批解码所需正文属性，把经过校验的属性值和事件位置放入本次调用的临时 SQL 表，完成剩余运算。只能下推必然成立的前置条件，不能把 `or` 的一个分支当作整个条件。

这个临时表仅在需要引用属性参与运算时使用，不保存完整事件，不跨调用复用，不成为持久化投影。它和本次连接、读取事务一起释放；取消时中断执行并清理。候选很多时，它仍会产生相应 I/O 或临时空间成本，`limit` 不承诺消除这些成本。

### 4.3 内存实现与持久化边界

MemoryTimelineStore 执行同一份表达式。它可以扫描已经持有的事实，但不能先为查询复制完整历史、克隆请求正文或逐条序列化完整事件。关联需要的键集合、分组结果属于本次计算，结束后释放；大小随参与运算的键数量变化。

这里减少的是读取产生的副本，不要求内存存储丢弃它拥有的原始事实。SQLite 的页缓存也不属于请求正文缓存。

复用既有表和列；提交标识等值查询采用[存储所有者的 v35 索引决定](appserver/native-storage-format.md#v35-submission-identity-index)。索引属于精确 schema，通过格式升级加入，不作为 v34 的无声扩展。后续增加索引须由[存储格式](appserver/native-storage-format.md)所有者决定兼容方式；严格 schema 校验下，不能把“只新增索引”默认为旧版本可读。

## 5. 状态恢复怎么改

`rebuild_facts` 的整段收集接口删除。以下是消费端需要完成的修改，事件含义和状态推进规则仍以各部件自己的契约为准。

| 所有者 | 读取方案 | 恢复时保留什么 |
| --- | --- | --- |
| Approval | 按 `approval_id` 查询有请求、无响应或取消的项。 | 结算所需标识；不读取已结束审批的调用正文。 |
| ModelProvider | 按 `turn_id`、`request_id` 查无 output-end 的调用，再读取这些调用的 tool-use-start 标识及参数完成状态；另读 steer、interrupt 与轮次控制字段。 | 结算字段及控制状态；结算函数改收这些字段，不再要求整个 `ModelCallData.request`。 |
| ToolExecutor | 按 `ToolResult.call_event_id` 排除已结束的 ToolCall，再选剩余项的 turn、request、call 标识；另读 interrupt 与轮次控制字段。 | 取消结果所需标识及中断状态；不恢复工具参数并重新执行。 |
| ContextPreparation | 查未完成的 prepare、自动 compaction-start，以及相关控制事实。 | 准备和取消状态；不恢复历史模型请求。 |
| InputQueue | 按当前输入成员、每项applied/withdraw及最新turn/interrupt读取；不重放八类历史，不保存完整队列快照。 | 队列和仍欠缺的决定；不能简化为“输入减去 consumed”。 |
| Loop | 查询已 applied、未 consumed 的输入；分别恢复当前轮次及未完成压缩的控制状态。 | 待消费输入和当前执行状态。输入可能早于本轮开始，不能统一从最近 turn-start 截断。 |
| Prompt、Permission、Wait 等 | 按各自契约查询最新记录、按键最新记录或未完成项；存在多步决定时继续有序处理所需字段。 | 当前有效配置或等待状态。 |
| Hooks | 装载只登记实时交接，不读历史；实际触发按身份及本轮位置查询。 | 无恢复快照；具体字段、轮次 tag 和兼容规则见 [Hooks §3.5](plugins/Hooks.md#35-loading-and-reads-at-hook-points)。 |
| BranchLine、Collaboration | 用现有状态机逐页消费所需字段；只有能证明旧事实不再影响决定时才收紧起点。 | 各自的业务状态，不额外保留事件列表。 |
| Goal | 按 [Goal 状态设计](plugins/Goal-state-read.md)索引读取最后一个完整业务状态；未结束则在内存暂停，不恢复执行。旧格式仅按兼容设计读取目标定义。 | 当前目标、judge 和有效状态；次数、轮次和评估是本实例内存，不重建旧控制流。 |
| BackgroundExec | 从生命周期字段恢复任务目录；未结束任务结算，缺少通知交接的终态继续处理。 | 契约要求的任务目录，包括仍需展示的已结束任务，不能全部删掉。 |

可以直接关联求集合的，返回集合；需要按顺序推进状态的，保留状态机。后一种方式仍须做到只读必要字段、逐页消费。不能为了消除所有遍历，再新增一套通用业务状态计算器。

恢复所写的结算事实仍经过 Timeline 和 Dispatcher。新查询接口不重放网络请求、工具、Hook 或子进程，也不改变恢复与实时事件的交接。

### 5.1 Goal 的读取与终止

[Goal 状态设计](plugins/Goal-state-read.md)定义 goal/state、内存执行、异常终止和加载暂停。加载不查询旧轮次、续行、任务或评估，不使用 source_through 推进 Goal 恢复；只恢复目标定义和有效暂停/结束状态。活 get 读内存，不能等待新的持久状态记录。

[旧格式与删除](plugins/Goal-property-queries.md)只处理必要的目标定义解释和业务回滚；其实际候选成本单列，不作为新格式普通加载的回退。Store 只执行现有 kind/位置及身份查询，不解析 Goal 文本或新增 Goal 状态接口。

## 6. 本次模型请求怎么构造

### 6.1 先确定内容，再读正文

上下文部件按以下顺序调用查询，规则仍由[上下文拼装需求 §2](context-assembly-requirements.md#2-业务需求)定义：

1. 固定 `ContextPrepare.through` 作为内容上界，取得各祖先的分叉边界。
2. 查询最新完成的压缩及其保留范围、采用关系、提示词和配置的有效记录。失败或未完成的压缩不能覆盖已完成结果。
3. 确定本次请求需要的事件位置、范围和内容字段。被固定保留的输入可以在压缩切点之前；被本轮采用的输入可以在本轮开始之前。
4. 分页读取这些内容，按既有投影规则构造消息，检查顺序、前缀和工具调用与结果的配对。事件正文处理完即释放；请求只保留自己使用的内容。
5. 生成本次 `ModelRequest`，交给发送、预算计算、压缩等实际消费者。

第 3 步的数据属于本次准备，不注册服务、不跨步骤缓存。确实需要有序处理的上下文事实仍逐页处理，不能通过读取并展开历次 `model/call.request` 来取得消息前缀。需要旧调用的 usage 或模型标识时只选这些字段。

读取失败、引用损坏或前缀不一致时不得发送缺内容的请求。已有允许回退的情况仍须证明结果完整，不能用空值补齐。

### 6.2 重试控制事实有独立范围

一次准备可能写入新的 compaction、budget 事实。重试需要读取这些事实，但不能因此把请求内容上界改为最新 head。

内容查询始终截止到原来的 `ContextPrepare.through`。重试控制查询只读该位置之后的本分支事实，另取一个固定上界，可以包含尚未发布的原子提交。它按事实契约中的轮次、请求和原始内容边界判断是否可复用；不能混入其他准备操作的结果。这个范围内的后续页仍使用同一个上界。

### 6.3 请求的持有与释放

删除 ContextPreparation 和 ContextPolicy 中跨准备调用保存完整 `ModelRequest` 的 `prepared` 字段。实际需要的当前请求移入本次操作的任务；同一次发送或准备过程的重试可以继续使用它，操作结束后不为下一次调用保留。

释放条件包含发送、重试、持久化和实时事实消费的完成，不能在仍有消费者时提前清空。业务可以保留小型运行状态，但不能把历史请求正文藏在状态对象或结果缓存里。历史查看、导出按其自身操作读取、消费和释放正文。

## 6A. 客户端首屏

CLI 主对话、line 模式、分支侧栏、成员对话和 ACP load/resume 必须按窗口打开。
具体停止条件、实时合流和跨窗口状态归 [clients 的首屏契约](clients.md#opening-a-conversation-with-a-bounded-window)，wire 与原子批次归 [history window](appserver/session-history-window.md)。

本改造提出的跨模块要求是：消费端不能仍从 0 收集完整历史；所需旧状态通过公开的状态或身份查询取得。首屏窗口与后台任务、待答问题、委派、待消费输入必须一起验收，不能以截断历史的方式丢掉控制功能。App Server 提供窗口接口不等于 CLI／ACP 已完成迁移。

## 6B. Recall 的候选与正文

Recall 的搜索答案是既有渲染规则得到的 thing 正文，不是事件 JSON，也不是单条 text delta。`about` 的每个词都必须出现在同一个 thing 的渲染正文中；大小写处理沿用 Recall 的 Unicode 小写规则。正文验证属于 Recall，存储不能根据字段命中就认定找到答案。

读取分成三步：

1. 查询候选的分支、事件位置、origin id 和关联键。候选按 chain 位置倒序，固定 `through`，用游标续读。`tool` 可以先筛 tool name；`before` 约束 thing 的排序锚点，不能截掉它所需的关联事实。
2. 按候选身份批量取它所需的输入采用关系、同 request 的文本片段、工具结果及所属轮次。输入正文以 `input/consumed` 归属轮次，回复按 request 拼接；分支内序号不能直接当作 chain 顺序。只读候选相关正文，渲染后逐词验证，保留命中项并释放未命中的正文。
3. 凑齐一页加一个已验证命中项后结束。多出的项决定是否有下一页。候选页为空但仍有续读位置时继续；候选很多、没有命中、分支有祖先都不能触发完整历史回退。

**全文索引是加速稀疏文本搜索所需的独立能力。** `Contains`、JSON `LIKE`、游标分页都不能把全文搜索变成索引查找。不建立全文索引时，只能承诺逐批扫描候选并释放正文，不能承诺 #1147 的“1 次索引候选查询 + 少量轮次读取”或与命中数量成正比的成本。

全文索引必须返回答案的超集。按事件 JSON 建 trigram 索引不满足此要求：词可能跨 text delta，大小写折叠可能改变字符，正文还包含渲染出的标签。索引至少要处理同 request 的拼接文本；短词、标点、CJK、渲染标签和无法证明覆盖的历史格式必须走明确的完整候选路径，不能悄悄漏报。索引不得保存第二份权威历史；写入、合并输出更新、删除、重建及旧库兼容由存储所有者定义。

全文索引采用 §6C 的候选契约和格式决定。索引只排除已证明不可能命中的候选，最终答案仍由 Recall 验证；不能直接照搬旧 PR 的“可能假阴性”行为来宣称覆盖搜索需求。

## 6C. 文本候选查询与 FTS5

`TextCandidate(field, partition_by, terms)` 是候选条件。字段为字符串时使用字符串内容，其余非空 JSON 值使用 JSON 文本；按事件顺序拼接同分组的字段，再进行 Unicode 小写转换。所有词都出现的事件必须保留。实现可以多返回候选，调用方必须验证业务正文。分组字段缺失的事件各自成组，不把所有缺少 request id 的输入合成一个组。

这个条件只能正向组合，不能放在 `Not` 内。它不改变普通字段条件、排序、分页和截止位置的含义。没有对应索引的存储可以保留所有候选；SQLite 对已建索引的属性使用 FTS5。没有索引的属性、不能安全索引的词、跨祖先段的拼接和未持久化尾部保留完整候选路径。

SQLite 建立两种属性索引：`data`（单事件），以及按 `kind`、`data.request_id` 分组的 `data.delta`。索引不保存正文：元数据表保存事件位置、属性名和分组键，contentless FTS5 表只保存 trigram 倒排项。`data` 按[原生存储格式](appserver/native-storage-format.md#v38收窄全文与关联索引的写入范围)的覆盖范围建立索引；历史请求、压缩正文和不透明扩展事实不进入索引，查询这些类型时仍保留候选。`data.delta` 在写入新片段时连同前 199 个字符建立倒排项，因此长度不超过 200 的 ASCII 词跨片段时仍有候选。每个词的 trigram 只要求同时出现，顺序和正文命中仍由 Recall 验证。

索引可排除由 3–200 个 ASCII 字母、数字及 `-`、`_`、`:`、`=` 组成的词。其他词不用于排除候选；混合查询可以使用其中安全的词缩小范围。索引更新与事件批次在同一 SQLite 事务中提交，合并物理输出行仍逐个登记逻辑事件。Session 复制按复制后的事实重建索引，删除同时删除索引。旧库在格式升级事务内回填，失败时连同格式标记一并回滚。

Recall 选择一个安全词，通过候选条件与关联键查询 origin 位置，最后读取并验证正文。选择一个词即可排除不可能命中的正文；其他词仍由正文验证，避免把跨事实的多个词误要求在同一条事实中命中。渲染生成的固定文字不能作为排除条件；无法由 request id 直接覆盖的审批、后台命令和委派结算保留相应工具 origin 候选。短词、CJK、标点和固定标签查询仍逐批消费候选，不收集整条历史。

FTS 表属于 v36；v35 仍只增加提交标识索引。v35→v36 是明确的单向格式升级，旧程序拒绝打开 v36。存储所有者的完整格式定义见 [native storage format](appserver/native-storage-format.md)。

### 7.2 改造顺序与兼容性

1. **查询契约与两个存储实现。** 先落实字段语义、完整范围、正文解码和分页；用同一组公开查询在内存与 SQLite 验证。旧接口迁移期间只委托新引擎，不维护两套筛选规则。
2. **入口及直接查询调用方。** 修改 Timeline、门面、TreeCommands 和语言绑定。按 id、最新记录、配置等查询先改为字段结果；普通门面不能因此获得未发布事实。
3. **恢复消费者。** 逐个完成第 5 节的恢复与实时交接验证，最后删除 `rebuild_facts` 及只服务于它的收集代码。
4. **请求构造。** 完成第 6 节的内容选择、正文消费和请求生命周期，删除两个 `prepared` 缓存；保留上下文结果一致性的流程验证。

这是 `query` 请求和结果的接口变更，不能声明为旧插件二进制或旧 TypeScript 调用的兼容扩展。Rust、服务绑定和随发行版交付的消费者必须一起迁移，生成 `npm/branch-services.d.ts`；若要支持独立升级的旧插件，须先由插件契约所有者确定接口版本策略，不能用字段别名或默认完整事件掩盖差异。

已有事件 wire fixtures 和模型请求序列化不变；数据库按存储所有者的 v35、v36 决定增加提交标识和派生文本索引，事件及正文编码不变。新查询的续读数据替代内部 offset，不自动改写 `session.history` 等客户端协议。

### 7.3 绑定位置

Rust 类型只在 runtime 定义一次，服务和存储端口共用查询表达式、分页及结果类型。存储范围是入口产生的内部类型，不暴露给插件。目标签名如下；具体序列化字段与第 2 节一一对应，不另建 Rust 专有语义。

```text
Timeline::query(TimelineQuery) -> Result<TimelineQueryReply>
Branch::query(TimelineQuery) -> Result<TimelineQueryReply>
Session::query(branch_id, TimelineQuery) -> Result<TimelineQueryReply>
TreeCommands::query(branch_id, TimelineQuery) -> Result<TimelineQueryReply>
TimelineStore::query(TimelineReadScope, QuerySpec, QueryPage) -> Result<QueryResult>
```

### 8.1 SQL 成本验收

使用一次性 SQLite 数据库，至少按 10 倍增长的历史规模比较以下查询：提交标识命中与未命中、最近一条控制事实、未结束操作的反关联、位置分页的首页与深页、正文参与条件、Recall 稀疏命中与零命中。两种分页方向都检查，并累计读完全部候选的所有分页成本；只测首页或某个深页不足以证明没有重复扫描。输入关联、模型文本/内容关联、工具关联的组合也要覆盖。合并输出、祖先和内存尾部另做结果一致性验证。

每个执行阶段记录 `EXPLAIN QUERY PLAN`、SQLite `VM_STEP`、`FULLSCAN_STEP`、`SORT`、`AUTOINDEX`，并记录内容节点加载、返回数据量、耗时及 Rust/SQLite 各自的峰值。`FULLSCAN_STEP=0` 不代表没有扫描：索引范围遍历不一定计入该项，必须结合 VM 步数增长和执行计划。选择阶段、正文候选阶段与内容解码分开列示，不能用其中一项冒充整个请求成本。

| 查询 | 计划与增长要求 |
| --- | --- |
| 提交标识 | `(session, branch, kind, submission_id)` 等值定位；不存在也不能扫描全部输入。若缺少索引，明确记录线性成本及所需格式决策。 |
| 最近事实 | 类型和位置索引反向取首条；不能排序全部正文再 LIMIT 1。 |
| 位置分页 | 游标限制下推到外层候选的位置范围；不对每页重读已经跳过的前缀。关联与分组仍使用原始固定范围，不能错误地随输出游标缩小。 |
| 未结束集合 | 等值关联使用索引或一次物化后的临时关联索引；数据翻 10 倍不能变成每条开始记录重新扫描全部终态的平方增长。 |
| 正文条件 | 先限定不依赖正文的候选，再解码条件用到的引用；分别报告候选数与节点数。 |
| Recall | 区分索引候选成本、正文验证成本和不可索引的完整候选路径；零命中也须测量。 |

已有索引是否足够由这些执行证据决定；新增必要索引必须补齐存储兼容决策，不把索引创建隐藏在普通查询中。性能分别记录扫描记录数、实际读取的内容节点数、返回数据量和峰值存活内存。`NOT EXISTS`、分组和正文搜索可能仍扫描大量候选，不能只用返回行数宣称查询成本降低。测试和测量只使用临时库或一次性副本，不修改用户数据库。

### 字符总数投影

`select: {kind: "characters", field}` 返回 `Count` 标量：所选记录中该字符串字段的
Unicode scalar 总数。缺失、null 和非字符串贡献 0；空集合返回 0。不接受分组、pick、排序
或分页。Memory 与 SQLite 使用相同的字符单位，包括字符串中的 NUL，不把 UTF-8 字节数
或 SQLite 的 NUL 截断长度当成字符数。该计算用于窗口外活动输出的绝对进度偏移；不把
正文返回客户端后再累计。

### 已选位置的返回

当投影只包含 `position`、`position.sequence`、`position.branch_id` 时，直接返回本次 SQL 已选出的分支与逻辑序号，不再次查询或解析正文。合并输出仍先由原输出规则确定逻辑位置。输出数组展开只能解析输出类型的正文，不能让 `json_each` 先解析压缩或其他非输出事实再按 kind 排除。
