# Compaction requirements

Status: Draft ([#428](https://github.com/arcships/dim/issues/428)). Requirements, not a design: this document fixes what good compaction means and what each owner must provide, and each owner designs its own part (§7). Scope: the context compaction of one branch. Chinese: [中文](../zh/design/compaction-quality.md).

A task can outlast the context window. Compaction exists so the agent keeps working after the window fills: the work continues, the user feels no drop in quality, and the user never has to repeat what was said. This document answers [#428](https://github.com/arcships/dim/issues/428)'s four questions, which [Agent context §2](agent-context.md#2-压缩) raises, and hands the consequences to the owners of the mechanism.

`B` is the input budget, `context_window − output_tokens`, as [ContextCompaction §5.1](plugins/ContextCompaction.md#51-productcontextmodel) defines it.

## 1. Answers

| # | Question | Answer |
| --- | --- | --- |
| 1 | What must survive compaction, and what may be lost because Recall can bring it back | Standing state, the running turn's inputs verbatim, a deterministic digest of the effects tools declare, and a model-written state summary survive. Exact past words, tool output and exploration may leave the context, because [Recall](plugins/Recall.md) reads the original events back (§3) |
| 2 | Do users need to know that compaction happened, or to trigger or control it | Users see it: a row with its state and outcome — completed, skipped, failed or cancelled — the insufficient-space mark of a completed one that could not reach the §5 bound, the summary, a standing usage gauge, a warning near the threshold, and `/compact`. Changing the threshold or turning automatic compaction off comes later (§4, §9) |
| 3 | What the cost bounds are | Linear in the session's total tokens, at most `0.5 × B` of context after a compaction, bounded summarizer work, and every compaction reports its own cost. Absolute seconds and prices are deliberately not set (§5) |
| 4 | How we judge that compaction works | Two checks: deterministic mechanism tests in CI, and a relative summary evaluation at the same budget (§6) |

## 2. Basis

Three general principles lead to the same layering.

1. **Context is a projection of facts.** The Timeline is the only source of truth, and compaction never changes it. A compaction is a snapshot of the projection: keyed state is a deterministic fold, and the summary is a lossy snapshot of what cannot be folded deterministically. Whatever can be derived deterministically from the facts is therefore not left to the model.

2. **Working set.** The window is fast memory and the Timeline is the backing store. Keyed state is pinned. The running turn and the recent tail are the working set. Recall pages content back in, but only when the model asks, so the summary must also work as an index of what can be recalled. When pinned state plus the working set exceed the window, compaction thrashes; that must be detected and reported, not repeated.

3. **Lossy coding at a fixed budget.** The budget is spent by value density: intent, the current work and decisions are dense; bulk tool output is sparse and recoverable. Distortion is only comparable at the same budget and on the same input, so quality evaluation is relative. Re-encoding accumulates distortion, so repeated compaction is the first thing to test.

## 3. What compaction keeps

A compaction keeps four classes of content and drops the rest.

| Class | Content | Guaranteed by | Size | Lifetime |
| --- | --- | --- | --- | --- |
| 1 Standing state | Keyed blocks: rules, the Goal, the `branch:line` identity, skills | Replay of the keyed baseline after every compaction | Bounded by each owner; replaced, never accumulated | Permanent |
| 2 Current work, verbatim | (a) Every input the running turn has consumed, whatever its producer: the task, mid-turn steers, inputs other plugins write. Keyed blocks are excluded: the keyed baseline already replays them, and pinning them would duplicate them. (b) The recent tail | (a) When the cut falls inside the running turn, the compaction copies these inputs verbatim into its replacement. (b) The tail keeps the most recent turns while the bound allows | (a) At most `0.1 × B` in total. Beyond that, a single input keeps its head and tail plus its Recall handle, the event id. (b) Up to `0.25 × B`, less when needed to reach the §5 bound | The running turn, and the recent tail |
| 3a Deterministic digest | The effects tools declare through the generic means of §7.4 — files written, commands with their exit status — and nothing else. It stays empty until a tool declares any; until then, changed files survive a compaction only as the exact identifiers 3b keeps | Generated by the compaction from Timeline facts, not written by the model | Bounded; the rest is reachable through Recall | Rolled forward |
| 3b State summary | Only what the facts cannot say: the task or goal in force; constraints and preferences still in force; standing decisions and their reasons; approaches ruled out and why; open items with the user (choices offered, questions pending); the current judgment; the next step; exact identifiers in use (paths, symbols, commands, errors) | The model's summary. Each compaction carries forward what is still in force, drops what was superseded, and reduces finished work to a line or nothing | Bounded; the target length is [#170](https://github.com/arcships/dim/issues/170)'s decision ([ContextCompaction §13.3](plugins/ContextCompaction.md#133-target-length)) | Permanent, but depends on the model's judgment |
| 4 Everything else | Exact past words, tool output, exploration | [Recall](plugins/Recall.md) reads the original events back | Takes no context | Permanent, on request |

**The task in force.** The first 3b item is the task or goal the user asked for and has not withdrawn; it stays required even when no Goal holds it. No prompt change: the wording is #429/#170's (§7.7).

**What may be lost from context.** Only class 4 may leave the context, and only because Recall returns the original events verbatim. Losing content is acceptable exactly where it stays reachable through Recall.

**Long sessions.** After a compaction the context is standing state, the digest, the state summary, the running turn and the tail. Its size does not depend on how long the session has run: a ten-turn session and a ten-thousand-turn session compact to the same shape. Keeping every user message verbatim is rejected for that reason: on a long session the user's words alone outgrow the window.

**Guidance for users.** What must never be forgotten belongs in standing state — a project rule or the Goal — which is a structural guarantee, replayed after every compaction. The summary is best effort, and Recall is the fallback.

**Lines.** Each line compacts on its own ([Timeline branches §1](timeline-branches.md#1-what-branches-are-for), [§7.2](timeline-branches.md#72-compaction)). How a line's identity and its inherited prefix survive a compaction is stated in [§7](timeline-branches.md#7-identity-and-context) and is not repeated here.

**Not required now.** If the chain evaluation (§6) shows constraints still in force decaying over repeated compactions, the next step is for compaction to write that part as keyed state. That is an option inside compaction's own facts, and it waits for that evidence.

## 4. What users see and control

All of the following is required, and all of it is the client's part.

- **A compaction row in the TUI.** Running, then its outcome — completed, skipped, failed or cancelled — and the insufficient-space mark of a completed compaction that could not reach the §5 bound.
- **The expanded compaction row shows only the summary body.** Hide the `<dim-summary>` … `</dim-summary>` markers and the runtime's fixed opening background notice and closing sentence when they wrap a summary. Keep unwrapped summary text and any such wording quoted within the summary unchanged. Do not display the digest or pinned inputs in this row. This presentation rule does not change the stored compaction record or the replacement sent to the model.
- **A `/compact` command**, wired to `session.context.compact`.
- **A standing context usage gauge.**
- **A warning as usage nears the automatic threshold.**
- **Localized texts.** The usage and compaction texts are localized like the rest of the TUI.

## 5. Cost bounds

Seconds and prices depend on the scenario, the model, the window and the cache state, so these bounds are structural and no absolute target is set.

- **Linear.** A compaction reads the previous summary and the entries newly cut, and nothing earlier. A session's total compaction cost therefore grows linearly with its total tokens, and one compaction's cost does not depend on how long the session has run.
- **Room.** The shares `0.5`, `0.25` and `0.1` in this document are provisional, and ContextCompaction sets them, like its retained share ([ContextCompaction §10](plugins/ContextCompaction.md#10-decisions-and-open-questions)). `B` is spent by the whole request: the system prompt, the messages and the tool declarations ([ContextCompaction §5.1](plugins/ContextCompaction.md#51-productcontextmodel)). The context after a compaction is at most `0.5 × B`, and the compaction reaches that by keeping less of the verbatim tail when needed, that is, by cutting later. Reaching `0.5 × B` leaves at least `0.3 × B` of work before the next trigger ([ContextCompaction §5.1](plugins/ContextCompaction.md#51-productcontextmodel) puts it between `0.8 × B` and `0.9 × B`).
  - It is marked **insufficient space** when the result cannot reach `0.5 × B`: when the parts it cannot shrink exceed `0.5 × B` on their own — the system prompt and the tool declarations, the keyed state, the pinned running-turn inputs, and the digest and the summary at their bounds — or when the summary exceeds its planned size and the result is still above `0.5 × B` after ContextCompaction re-plans the cut once with the summary's actual size. The mark names the parts that cover the excess, largest first, and how the fact carries it is ContextCompaction's design.
  - Automatic compaction does not run again until at least `0.25 × B` of new history has accumulated since the previous attempt. Budget recovery is the exception. Without this rule, when the parts compaction cannot shrink sit near the trigger, each new step would start another compaction, because each step makes the history different. After a compaction that reaches `0.5 × B`, the trigger is already further away (above), so the rule binds only in that case.
  - Budget recovery may compact once more; if the request still does not fit after that, the request fails with an error that names the resident part, rather than compacting again.
- **Bounded work.** The summarizer requests of one compaction are at most the chunk count plus a fixed retry count. Every failure path ends in a recorded outcome. A failed or cancelled compaction never applies.
- **Self-reported cost.** Every compaction's fact carries its summarizer's input, output and cache tokens, its request count, its duration, and the context size before and after; where they sit in the fact is ContextCompaction's design. `/usage` and the compaction row show them, so each real session shows what its compactions cost.

## 6. How we judge that it works

| Check | What it verifies | Pass | Where |
| --- | --- | --- | --- |
| Mechanism tests | Class 1 replay. Class 2: the running turn's inputs present verbatim, keyed blocks not duplicated, the `0.1 × B` limit, head and tail with the handle, and the tail, up to `0.25 × B` and shorter when §5 needs it. Class 3a matches the declared effects. Every cut entry the model had in its context is readable verbatim through Recall ([Recall §14](plugins/Recall.md#14-acceptance-flow-tests), flow 4). The §5 bounds: linear reads, the `0.5 × B` bound with the mark on every result that cannot reach it, the `0.25 × B` regrowth rule, the recovery limit, bounded requests, a failed or cancelled compaction not applied, deterministic replay. A substantive summary: non-empty, with its required parts present | All pass, deterministic, with a mock model | CI |
| Relative summary evaluation | Class 3b: each required item kept, and nothing that a case's `absent` probe names presented as current. Includes the **compaction chain**: a `fact` probe for an early constraint after the fifth compaction, and an `absent` probe for a constraint withdrawn midway | Same cases, same model, **same budget**, against the current strategy: [model-facing prompts §8.1's test](model-prompts.md#81-the-rule) on the metrics [ContextCompaction §13.4](plugins/ContextCompaction.md#134-evaluation) defines — fact recall `F`, exact recall `X`, the violation rate `V`, the failed-run rate and the unjudged-run rate — with `δ = 0.05`, Holm at a family-wise `α = 0.10`, and the floor of 20 judged runs of every case per arm. Either the summary length is fixed, or the length is reported beside every score. Run when the summary prompt, model or strategy changes | Locally, with `xtask summary-eval` ([#170](https://github.com/arcships/dim/issues/170)) |

Absolute pass lines are not used. A task success rate measured against an uncompacted run varies by scenario and model and needs many runs to separate a difference from noise. A relative comparison at the same budget holds across scenarios, so the summary evaluation is what gates a change to the summary prompt, the model or the strategy.

A session-level check on a real model is not used. One run of a nondeterministic model would be an absolute pass line, which the paragraph above rejects. What it would ask is covered elsewhere. The task, a constraint given at the start and the next step are 3b `fact` probes, and the chain carries the constraint; that is consistent with [ContextCompaction §13.7](plugins/ContextCompaction.md#137-ablation-review), which removed the continuation probe. A datum that appeared only in a cut tool output is readable verbatim through Recall ([Recall §14](plugins/Recall.md#14-acceptance-flow-tests), flows 4–5), and a case's `absent` probe catches a summary that gives it a value the output did not contain.

## 7. Requirements to owners

Each subsection names one owner and what this document requires of it. The owner changes its own document; this one does not. The format follows [Timeline branches §17](timeline-branches.md#17-requirements-raised-to-mechanism-owners) and [§12.2](timeline-branches.md#122-items-for-the-prompt-layer-429).

### 7.1 ContextCompaction

**Owner:** ContextCompaction; implemented under [#528](https://github.com/arcships/dim/issues/528).

- **Class 2(a) pinning.** When the cut falls inside the running turn, the replacement carries every input that turn has consumed, whatever its producer, verbatim, within `0.1 × B`. Keyed blocks are not pinned, because the keyed baseline replays them. Beyond the limit, a single input keeps its head and tail and its event-id handle.
- **The class 3a digest.** Generate it from the effects tools declare through the generic means of §7.4, from Timeline facts and not from the model. Read no tool's input schema: a tool's effects reach the digest only through its declaration. Raise the need for that means to its owner (§7.4).
- **The class 3b structure.** The summary carries the required parts of §3, the task or goal in force first, drops what was superseded, and reduces finished work to a line or nothing.
- **The §5 rules.** Keep the verbatim tail at or below `0.25 × B`, and cut later when the `0.5 × B` bound needs it. Mark insufficient space when the result cannot reach `0.5 × B` — when the parts compaction cannot shrink exceed `0.5 × B` themselves, or when the summary exceeds its planned size and the result is still above `0.5 × B` after the cut is re-planned once with the summary's actual size — and name the parts that cover the excess, largest first. Run automatic compaction again only after at least `0.25 × B` of new history since the previous attempt; budget recovery may compact once more and never again. How the mark and the cost fields are recorded is the owner's design.
- **Linear rolling.** Read the previous summary and the newly cut entries, and nothing earlier.
- **The cost diagnostics** of §5.
- **The substantive-summary check.** Non-empty, with its required parts present.
- **The stale §1 sentence.** [ContextCompaction §1](plugins/ContextCompaction.md#1-summary) says automatic compaction "never runs in production" and cites `main.rs`. It runs there: the product and `--models` profiles install compaction through `defaults::install_compaction` ([cli.rs:308](../../crates/dim-app-server/src/cli.rs)), and only the mock profile binds `ContextModelHost(None)`. The owner corrects its own text.

### 7.2 Recall

**Owner:** Recall; implemented under [#529](https://github.com/arcships/dim/issues/529).

The tool description says that Recall reads history from before a compaction, and that the handles carried in pinned inputs are its ids. Today the description says it recalls what happened earlier in the conversation, without saying that a compaction is not its boundary ([recall.rs](../../crates/dim-agent-capabilities/src/recall.rs)); the behaviour is already stated in [Recall §1](plugins/Recall.md#1-problem-and-scope).

### 7.3 WorkspaceTools (FileReads)

**Owner:** WorkspaceTools (FileReads); implemented under [#524](https://github.com/arcships/dim/issues/524).

A `write` that replaces an existing file needs a read that is still in the context. After a completed compaction cuts out the operation that bound the file, `write` refuses until any read of the file, a part included. `edit` keeps its binding, because its exact `oldText` match checks the content itself. A read in the kept tail still counts. A binding is what the model has seen of a file on this branch, and the bindings live in branch memory, which compaction never touches ([file_reads.rs](../../crates/dim-agent-capabilities/src/workspace_tools/file_reads.rs)). The owner designs how, from the branch's own facts.

### 7.4 ToolRegistry (the tool contract)

**Owner:** ToolRegistry; implemented under [#527](https://github.com/arcships/dim/issues/527).

A tool that wants its effects in the digest declares them through a generic means, such as the files it wrote or the commands it ran with their exit status. Providing that means is this owner's design; ContextCompaction raises the need and does not design it. Until a tool declares its effects through it, the digest stays empty.

### 7.5 CLI and TUI

**Owner:** CLI and TUI; implemented under [#530](https://github.com/arcships/dim/issues/530).

The list in §4, and nothing else. The gap #530 closed: the projection dropped both compaction events, so the row, its running state, its outcome and the summary never reached the user ([projection.rs](../../crates/dim-cli/src/projection.rs)); the command list had no `/compact` ([commands.rs](../../crates/dim-cli/src/ui/commands.rs)), and no client called the `session.context.compact` method that already existed ([context_methods.rs](../../crates/dim-agent-capabilities/src/context_methods.rs)); nothing warned as usage neared the threshold, which only `/usage` showed; the recorded summary was reachable only through an export, which wrote the raw `context/compaction` event and its `replacement` ([export.rs](../../crates/dim-cli/src/export.rs), [storage/export.rs](../../crates/dim-app-server/src/storage/export.rs)); and a compaction that completed outside a run refreshed nothing, so the reading stayed stale until the next refresh. The §4 gauge is the `input / window` reading shown with the composer ([tui.rs:4192-4204](../../crates/dim-cli/src/ui/tui.rs)); `poll_context` ([session_host.rs:1641-1651](../../crates/dim-cli/src/session_host.rs)) spends one `session.context.usage` read on the first poll after the reading is marked stale: entering a session ([session_host.rs:795](../../crates/dim-cli/src/session_host.rs)), a model switch ([session_host.rs:2833](../../crates/dim-cli/src/session_host.rs)), each finished model request on `main` ([session_host.rs:1761](../../crates/dim-cli/src/session_host.rs)), a run on `main` ending ([session_host.rs:1795](../../crates/dim-cli/src/session_host.rs)) and a compaction result on `main` ([session_host.rs:3391-3393](../../crates/dim-cli/src/session_host.rs)).

### 7.6 Summary evaluation (#170)

**Owner:** Summary evaluation; implemented under [#170](https://github.com/arcships/dim/issues/170).

[#170](https://github.com/arcships/dim/issues/170) adds, in the runner of [ContextCompaction §13.4](plugins/ContextCompaction.md#134-evaluation):

- **(a) Candidate arms.** A candidate summary prompt or strategy runs beside the current one on the same cases, through the shipped strategy and not an evaluation-only path. How, for example as factory configuration like the target rule, is #170's design.
- **(b) Chained cases.** A case compacts five times in sequence. Each summary becomes the next compaction's earlier summary, with the next slice of messages.
- **(c) The 3b probes** of §6, including the task in force (§3).

### 7.7 Model-facing prompts (#429)

**Owner:** Model-facing prompts; implemented under [#429](https://github.com/arcships/dim/issues/429).

The summary prompt's wording is product policy. A change to it goes through the relative evaluation of §6. The prompt is the fixed one at [summary_strategy.rs:19](../../crates/dim-agent-capabilities/src/summary_strategy.rs).

The requirements for this text, and for the rest of the prompt layer, are in [Model-facing prompts](model-prompts.md).

## 8. Rule check

Against [design rules §4](../architecture/rust-agent/principles.md#4-通过时间线扩展行为):

| Rule | Answer |
| --- | --- |
| 1 Command events | `session.context.compact` already makes the Loop's own state change through a command its owner serves; this document adds none |
| 2 Handoff | Not applicable: the replacement is part of the completed fact the projection replays |
| 3 Before callbacks | Not applicable |
| 4 No business meaning in core | The digest is generated inside the compaction strategy from public facts; no core part gains a case |
| 5 Batches | A compaction stays one result fact; the digest and the summary travel in its existing `replacement` |
| 6 Context from handed-over events | The replacement reaches the model only through the projection of a completed fact; a Recall result only as a tool result |
| 7 Public events and services | The requirements use public Timeline facts, the existing record, `session.context` and the tool table; no new service |
| 8 Infrastructure unchanged | Timeline, Dispatcher, the event envelope and format, snapshot anchoring, and the Session and branch facades are untouched; every requirement is met inside an owner's own events, state and flow. Evidence below |
| 9 Only facts later decisions use | No new event: the compaction record, extended by its owner, is the one fact |

**Rule 8, with evidence.** No requirement reaches infrastructure:

- Class 2 uses the compaction record's existing `replacement` and replay rule ([ContextCompaction §2.2](plugins/ContextCompaction.md#22-extension-points), [§4.3](plugins/ContextCompaction.md#43-events)).
- FileReads folds the existing public `context/compaction` fact on its own branch; it needs no new event and no new service.
- Nothing is added to the Timeline for the UI: the TUI reads the existing `context/compaction-start` and `context/compaction`, which [§4.3](plugins/ContextCompaction.md#43-events) already lists for clients.

**Rules 1 and 7.** No requirement has one plugin decide for another or read another's state: ContextCompaction does not call FileReads, FileReads reacts to the public fact, and the TUI uses the existing session method.

**The later option.** Writing in-force constraints as keyed state is an option inside ContextCompaction's own facts. It is not a Timeline or infrastructure change, this document does not decide its mechanism, and it waits for the chain evidence (§3).

Being requirements, the document adds no part, service, event, method or configuration; the owners' designs answer the remaining rules.

## 9. Later options

- **Changing the automatic threshold.** It is a provisional heuristic in code ([ContextCompaction §10](plugins/ContextCompaction.md#10-decisions-and-open-questions)); a setting needs a decision about its scope.
- **Turning automatic compaction off**, for a user who prefers to compact by hand. It also decides what a full window does then.
- **A focus for `/compact`**, for example "compact the decisions so far". It needs an input to the summary strategy; the method's input is `{sessionId, branchId}`.
- **Constraints and open decisions as keyed state**, once the chain evaluation shows them decaying (§3).
