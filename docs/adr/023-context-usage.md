# 023: 上下文用量由独立分支部件维护

Decision status: Accepted.

## Context

上下文用量用于显示当前占用、检查请求预算和决定是否压缩。查询用量时重建消息，会把正文读取、历史折叠和消息组装的开销带进 resume。把查询改成异步只改变等待关系。

用量是有效上下文变化产生的统计结果。输入被采用、模型输出结算、工具结果进入上下文、配置变化和压缩替换都可能改变它；这些变化不只发生在准备请求期间。统计需要独立的状态所有者，并与请求构造共用上下文语义。

## Decision

### D1. ContextUsage 是现有上下文功能内的独立分支部件

`ContextUsage` 拥有本分支的用量统计、对应位置、服务商校准基准及其持久化和恢复。它随现有上下文功能安装，不另设一个需要用户单独启用的功能插件。

它按分支事实推进状态，属于 [Capability](../design/plugin-contract.md#6-capability)。它不是转发服务，也不拥有完整历史、请求正文或消息缓存。

| 对象 | 责任 |
| --- | --- |
| ContextUsage | 维护和查询统计，处理服务商用量校准，恢复自己的统计状态。 |
| 上下文投影 | 定义哪些内容有效，以及内容的合并、移除和替换；统计和请求构造共用这些规则。 |
| 计数实现 | 定义内容的统计贡献、估算算法及算法的适用条件。 |
| ContextPreparation | 构造请求，使用统计做预算检查和压缩决策；不再拥有另一套累计统计。 |
| Timeline 与存储 | 提供通用的事实、位置和持久化能力，不解释输入采用、token 或服务商校准。 |
| 客户端与 Session 方法 | 经公开入口读取统计，不在查询时渲染历史。 |

### D2. 统计随有效上下文变化推进

统计范围包括消息、system 和 tools。统计依据是[上下文拼装需求](../design/context-assembly-requirements.md)所定义的有效内容；事件条数、原始正文长度和所有历史 usage 的总和都不能代替它。

| 变化 | 统计操作 |
| --- | --- |
| 输入被消费并形成上下文消息 | 加入实际进入上下文的消息贡献；排队或仅已交接的输入不提前计入。 |
| 模型输出结算 | 按完成或中断后的保留内容结算；连续 delta 合并和完整内容覆盖遵循同一投影规则。 |
| 工具结果进入上下文 | 加入结果及其附带上下文消息的贡献。 |
| system 或 tools 变化 | 替换对应贡献。 |
| 压缩完成 | 移除被替换前缀的贡献，加入 replacement 和保留基线；失败或跳过不执行替换。 |

统计只做内容变化要求的工作，已经计入且未变化的正文不因查询再次读取。计数实现支持可组合统计时，复用该能力；不假定所有可替换的计数实现都能用字节相加。

### D3. 服务商 usage 校准对应请求的基准

服务商返回的实际输入用量通过已有事实进入统计。ContextUsage 将其与对应请求、模型配置、上下文前缀和统计位置匹配，用于校准该前缀的估算，并保留其后新增内容的统计。

同一请求的后续用量记录更新该请求的基准，不重复累加。已经被压缩替换或不再匹配的前缀，不使用旧请求的实测值校准当前统计。

`total_tokens` 不代表当前上下文大小；`completion_tokens` 不直接作为下一次请求新增消息的贡献；缓存输入也不能在实际输入总量之外再加一次。返回结果区分本地估算和含服务商基准的估算，不能把混合结果称为全部由服务商实测。

### D4. 查询当前统计，不通过查询触发历史重建

用量读取对应明确的分支和截止位置，不返回一个无法说明位置的旧数值。客户端显示与准备请求使用同一计数和基准适用规则。

正常 resume 从持久统计取得当前结果，不以重读历史正文补齐滞后的周期快照作为常规路径。没有可复用服务商基准时仍可使用本地估算，不因此自动重建整个请求。

旧数据初始化、统计缺失或失效时如何重建和返回，由后续设计明确；这些路径须与正常读取区分，不能静默退回每次查询遍历历史。没有可用配置或计数实现时，返回有业务含义的不可用结果，不为最后返回错误先渲染正文。

### D5. 持久化保存统计，不追加逐事件的 usage 日志

ContextUsage 的持久状态保存统计贡献、累计结果、适用基准和恢复所需身份；不复制完整事件或上下文正文。仅用于流式展示、尚未改变有效上下文的 delta 不逐条触发持久统计写入。同一原子批次内的统计变化应合并处理。

不按每个接收到的事件追加一条 usage 事实，也不承诺每个请求只增加一次写入。需要保持当前统计时，持久化成本由实际影响统计的变更决定。

事实提交、异步派发和统计持久化之间的一致性必须在后续设计中闭环。独立部件或现有恢复快照本身不提供这一保证。本决策不授权把业务计算放进存储、不改变提交和发布规则，也不选择数据库格式。

## Consequences

### 方案轮廓

以下是目标处理流程，不是现有装配图：

```text
上下文相关事实与服务商用量
  -> ContextUsage 按序处理
     -> 复用上下文投影规则，计算统计变化
     -> 更新当前统计及适用基准
     -> 按后续设计确定的提交约定持久化

客户端用量读取 / 请求预算检查
  -> 经各自公开入口读取 ContextUsage
  -> 返回指定位置的统计，不触发历史渲染
```

实际请求经过 host 或写入前变换后，仍须检查最终请求预算。统计覆盖的上下文前缀与请求专有的增补或变化必须区分，不能用分支统计替代最终请求校验，也不能为校验重新扫描未变化的历史。

后续具体设计需要确定：

1. 统计数据、计数算法标识、服务和读取结果，以及基准适用条件。
2. ContextUsage 如何复用投影规则、消费事实并交接实时处理；未完成输出等必要状态的内存边界。
3. 持久统计与事实的位置和提交关系；崩溃、保存失败、异步派发落后及恢复缺失时的行为。不能把需要补算的历史从 usage 查询移到 attach 后称为问题已解决。
4. 分叉和祖先截止、配置变化、压缩替换、迟到或重复 usage 的处理。
5. 旧数据初始化、兼容性及所需通用机制。涉及存储格式或提交合同的变更，由机制所有者另行决定。
6. 与完整投影计数的等价验证，以及新增写入、计算次数、正文读取量和 SQL 扫描量的验收。

仅返回少量数字不代表数据库扫描少。验收须区分已有持久统计的正常恢复与首次初始化；扩大已结束历史时，正常读取不能重复加载或遍历其正文。

## Non-goals

不在本 ADR 定义具体 API、事件字段、表结构、索引、快照格式或写入事务方案；不选择新的 token 算法；不改变上下文内容、模型请求和压缩质量。具体 design 不把提案中的服务当作已经存在的依赖。

## Supersession

不替代既有 ADR。沿用 [ADR 021](021-reads-follow-the-state-owner.md) 的状态读取归属与 [ADR 022](022-event-property-queries.md) 的查询边界；ContextUsage 是业务统计所有者，不是读取层缓存或通用投影服务。

后续设计据本决策调整[ContextCompaction](../design/plugins/ContextCompaction.md)中用量由 ContextPreparation 直接提供的职责约定；计数、预算和机制各自由其所有者细化。
